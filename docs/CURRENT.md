# สถานะงานล่าสุด

อัปเดต: 17 พฤศจิกายน 2026

## ชื่อเมนูตรวจสอบคุณภาพ

- เปลี่ยนชื่อเมนูและหัวข้อหน้า QC เป็น **ตรวจสอบคุณภาพ(QC)** บน `lthai-docker` แล้ว ตรวจชื่อในชุดเว็บที่เปิดใช้งานและยืนยันว่าเว็บกับ API health ตอบ HTTP 200 ชุดทดสอบเว็บผ่าน 22 รายการ

## รหัสผ่านขั้นต่ำ 10 ตัวอักษร

- ใช้ขั้นต่ำ 10 ตัวอักษรทุกครั้งที่ตั้งรหัสผ่าน ได้แก่ ตั้งผู้ดูแลคนแรก เพิ่มบัญชี เปลี่ยนรหัสผ่านของตนเอง และตั้งรหัสผ่านใหม่ให้บัญชีเดิม
- ทดสอบ API บนฐานแยกว่าปฏิเสธ 9 ตัวอักษรและรับ 10 ตัวอักษรครบทั้งสี่กรณี `npm run check` และ `npm run build` ผ่าน `npm test` ผ่าน 89 รายการ ข้ามชุดนำเข้าชาร์ตสีที่ต้องใช้ Python 5 รายการ ลบฐานทดสอบแล้ว
- สำรองฐานหลักไว้ที่ `data/backups/password-live-25691117-110028-497/` และตรวจ SHA-256 ก่อนอัปเดตเว็บและ API ของ `lthai-docker` เว็บและ API health ตอบ HTTP 200 ตรวจข้อความบนเว็บว่าใช้ขั้นต่ำ 10 ตัวอักษร และทดสอบตัวตรวจรหัสผ่านใน API ที่รันจริงว่าปฏิเสธ 9 และรับ 10 ตัวอักษร ข้อมูลบัญชีเดิมทั้ง 2 บัญชีตรงกับก่อนอัปเดต

## แยกเมนูงานชุบเคลือบ งานเตา และ QC

- ผู้ใช้ยืนยันแยกสามเมนูหลักและหน้าจอสำหรับพัฒนาต่อ ใช้สิทธิ์และ API เดิม งานชุบแสดงเฉพาะใบเบิกสำหรับชุบ งานเตาแสดงใบเบิกบรีสรอยืนยันและมีปุ่ม **ไปคัด QC** สำหรับรอบที่เผาเสร็จแล้วยังคัดไม่ครบ หน้า QC มีคิวรอคัด ฟอร์มลงผล ยอดพร้อมส่ง และทางไปสินค้าสำเร็จ
- กู้ฐาน QA จาก `data/backups/docker-25691117-091945-144/` ตรวจ Chrome ตั้งแต่ยืนยันใบเบิกบรีสในงานเตาถึงลงผลจากลิงก์ของรอบเผา ได้พร้อมส่ง 45 แผ่น และส่วนเกิน 5 แผ่นไปหน้าสต็อก `npm run check` และ Docker web build ผ่าน `npm test` ผ่าน 88 รายการ ข้ามชุดนำเข้าชาร์ตสีที่ต้องใช้ Python 5 รายการ
- สำรองฐานหลักที่ `data/backups/docker-25691117-092436-552/` และตรวจ SHA-256 ก่อนอัปเดตเว็บของ `lthai-docker` เว็บและ API health ตอบ HTTP 200 แฮชข้อมูลใบเบิก ชุดชุบ รอบเผา รายการลงเตา QC ยอดพร้อมส่ง และรับเข้าสต็อกตรงกันครบเจ็ดตารางและวิว ลบฐาน QA และปิดพอร์ตทดสอบแล้ว

## เมนูสต็อกแยกเปิดใช้บนชุดหลัก

- ผู้ใช้ยืนยันเมนูหลัก **สต็อก** มีแท็บ **ดินปั๊มและเบิก** กับ **สินค้าสำเร็จ** แท็บแรกย้ายยอดดินปั๊มและใบเบิกมาไว้ด้วยกัน แท็บหลังรวมรายการรอรับจาก QC ยอดรับสุทธิ และประวัติรับเข้าและย้อนรับ งานชุบ เตา และ QC ยังแสดง **ยอดพร้อมส่ง** และ **สต็อกงานรอเผา** พร้อมปุ่มไปที่สินค้าสำเร็จสำหรับผลคัดที่มีส่วนเกินพร้อมรับเข้า
- ใช้ API และสิทธิ์เดิม แสดงแท็บดินปั๊มตามสิทธิ์ดูงานปั๊ม และแท็บสินค้าสำเร็จตามสิทธิ์ดูงานชุบ เตา และ QC เพิ่มคำศัพท์สต็อกดินปั๊มและยอดพร้อมส่งใน [GLOSSARY.md](../GLOSSARY.md)
- ซ้อมบนฐานแยกจาก `data/backups/docker-25691117-084502-506/` ตรวจ Chrome ว่าเปิดฟอร์มยอดตั้งต้นได้ ดูยอดพร้อมส่งแยกได้ และย้อนรับ → เปิดสินค้าสำเร็จจาก QC → รับกลับจากหน้าใหม่ได้ `npm run check` และ Docker web build ผ่าน `npm test` ผ่าน 87 รายการ ข้ามชุดนำเข้าชาร์ตสี 5 รายการที่ต้องใช้ Python
- สำรองฐานหลักที่ `data/backups/docker-25691117-085024-401/` และตรวจ SHA-256 ก่อนอัปเดตเฉพาะเว็บใน `lthai-docker` แฮชของสต็อก ใบเบิก QC ยอดพร้อมส่งและการรับเข้าตรงกันครบเจ็ดตารางและวิว เว็บและ API health ตอบ HTTP 200 ลบฐาน QA และปิดพอร์ตทดสอบแล้ว

## ลบผลคัดเดิมจากงานปั๊ม

- ผู้ใช้ยืนยันให้เอาปุ่ม **ประวัติผลคัดเดิม** ออกและลบรายการเก่าจากฐานหลัก โค้ดเลิกเปิดให้อ่านหรือเขียนผ่าน API เดิม ให้ลงผลคัดใหม่ใน **งานชุบ เตา และ QC**
- สำรองและซ้อมลบบนฐานแยกจาก `data/backups/docker-25691117-082521-788/` ตรวจ Chrome แล้วว่าปุ่มหายและผลคัด QC ยังเปิดได้ `npm run check` และการ build อิมเมจ Docker ผ่าน `npm test` ผ่าน 86 รายการ ข้ามชุดนำเข้าชาร์ตสีที่ต้องใช้ Python 5 รายการ
- สำรองฐานหลักที่ `data/backups/docker-25691117-082721-028/` และตรวจ SHA-256 ก่อนอัปเดตเว็บและ API แล้วลบงานเผาเดิม 1 รายการและผลคัดเดิม 1 รายการในฐาน `lthai` ตรวจแล้วว่าเหลือ 0 แถวครบสามตารางเดิม ข้อมูลที่ตรวจ 11 ตารางและวิวตรงกันก่อนและหลังลบ รวมถึง QC ใบเบิก ยอดพร้อมส่งและสต็อก เว็บและ API health ตอบ HTTP 200 ลบฐาน QA และปิดพอร์ตทดสอบแล้ว

## ลงผลคัดหลังเผาผ่าน QC

- ผู้ใช้ยืนยันถอดแท็บ **ผลคัด** จากงานปั๊ม ให้บันทึกผลคัดใหม่ใน **งานชุบ เตา และ QC** และเก็บข้อมูลเดิมให้เปิดดูได้จากปุ่ม **ประวัติผลคัดเดิม** ที่งานปั๊ม
- หน้าเว็บโหลดประวัติเมื่อเปิดดู API งานเผาและผลคัดเดิมยังอ่านได้ตามสิทธิ์ดูงานปั๊ม และปฏิเสธการเพิ่มหรือแก้ด้วย HTTP 410 เก็บผลคัดย้อนหลังและทุกฉบับแก้ไขไว้ในฐานเดิม
- ซ้อมบนฐานแยกจาก `data/backups/docker-25691117-081149-049/` ตรวจ Chrome ว่างานปั๊มเหลือสามแท็บ เปิดประวัติแบบอ่านอย่างเดียวได้ และผลคัด QC ยังเปิดได้ `npm run check` และการ build อิมเมจ Docker ผ่าน `npm test` ผ่าน 86 รายการ ข้าม 5 รายการนำเข้าชาร์ตสีที่ต้องใช้ Python
- อัปเดตเว็บและ API ของ `lthai-docker` หลังสำรองฐานหลักที่ `data/backups/docker-25691117-081631-491/` และตรวจ SHA-256 เว็บและ API health ตอบ HTTP 200 แฮชของข้อมูลก่อนและหลังตรงกันทั้งแปดตารางที่ตรวจ ครอบคลุมผลคัดเดิม ใบเบิก ใบสั่ง QC การจัดสรร และยอดรับเข้าสินค้าสำเร็จ ลบฐาน QA และปิดพอร์ตทดสอบแล้ว

## เมนูหมวดหมู่เปิดใช้บนชุดหลัก

- ผู้ใช้ยืนยันให้ย้าย **ทะเบียนกระเบื้อง**, **ชาร์ตสี** และ **ช่วงอุณหภูมิ** มาเป็นแท็บของเมนูหลัก **หมวดหมู่** ใช้สิทธิ์รายหน้าเดิม รายละเอียดอยู่ใน [บันทึกความต้องการ](discovery.md#เมนูหมวดหมู่)

- `npm run check` และชุดทดสอบเว็บ 20 รายการผ่าน สร้างอิมเมจเว็บ Docker และทดสอบ Chrome ที่หน้าจอเดสก์ท็อปและกว้าง 390 พิกเซล ตรวจบัญชีผู้ดูแล บัญชีดูเฉพาะชาร์ตสี บัญชีดูเฉพาะช่วงอุณหภูมิ และบัญชีที่ไม่มีสิทธิ์เปิดหมวดหมู่

## งานชุบเคลือบ งานเตา และ QC เปิดใช้บนชุดหลัก

- ผู้ใช้ยืนยันขอบเขตใน [แบบงานชุบเคลือบและงานเตา](superpowers/specs/2026-11-16-glazing-kiln-design.md) แล้ว คำตอบระหว่างเก็บความต้องการอยู่ใน [บันทึกความต้องการ](discovery.md#งานชุบเคลือบและงานเตา-ข้อสรุปรอบแรก-2026-11-16) และคำศัพท์อยู่ใน [GLOSSARY.md](../GLOSSARY.md)
- เส้นทางงานคือ ออเดอร์ → ปั๊มพร้อมเผื่อ 5–20% → ชุบ → เข้าเตาตามช่วงอุณหภูมิของดินและสี → คัด QC → เตรียมส่งออเดอร์ ส่วนเกินที่ผ่านคัดเข้าสต็อกสินค้าสำเร็จเมื่อผู้มีสิทธิ์ตรวจและยืนยัน
- ใบต้นทางย้ายดินปั๊มข้ามใบได้เฉพาะส่วนเกินจากเป้าปั๊มรวมเผื่อ ใบสั่งและใบเบิกเก่าที่ค้างทำต่อได้หลังตรวจยอดและเติมข้อมูลที่ขาด
- พัฒนาตาม [แผนงาน](superpowers/plans/2026-11-16-glazing-kiln.md) เพิ่ม API ใน `apps/api/src/finishing/` หน้าจอใน `apps/web/src/components/finishing/` และเชื่อมใบสั่งกับการเบิกในโมดูลปั๊ม ใช้ผลคัดเดิมเป็นประวัติและใช้รายการใหม่คำนวณยอดพร้อมส่งกับสต็อกสินค้าสำเร็จ
- งานเก่าเริ่มใช้ได้เมื่อเติมข้อมูลใบสั่งและยืนยันเฉพาะยอดค้างของแต่ละใบเบิก แหล่งสต็อกเก่าที่ไม่มีชนิดดินบันทึกแยกใช้ชนิดดินจากทะเบียน ณ เวลาที่รัน migration ให้ตรวจดินและยอดจริงก่อนยืนยันงานค้าง
- รอบทดสอบกู้ฐานแยก `lthai_glazing_qa_20261116` จาก `data/backups/glazing-25691116-113632/lthai.dump` หลังเทียบ SHA-256 แล้ว และทดสอบผ่านเว็บ QA ที่พอร์ต 3129
- ตรวจด้วย `npm run check`, `git diff --check` และ `npm test` เปิด ชุดทดสอบส่งงานข้ามเครื่องเดิม ผ่าน 97 รายการ ข้าม 5 รายการนำเข้าชาร์ตสีที่ต้องใช้ Python ทดสอบ API ครอบคลุมบรีสและใบค้าง การย้ายยอดข้ามใบ การส่งซ้ำ การแบ่งลงเตา ผลคัดรวม และการย้อนยอดปลายทาง ทดสอบ Chrome บนเดสก์ท็อปและ 390 พิกเซล ได้พร้อมส่ง 1,000 แผ่นและรับส่วนเกิน 50 แผ่น
- ผู้ใช้ตรวจรับและยืนยันให้ล้างทะเบียนกระเบื้อง ช่วงอุณหภูมิ งานปั๊ม งานชุบ งานเตา QC และยอดสินค้าสำเร็จในฐานหลัก ซ้อมกู้และล้างในฐานแยกก่อน จากนั้นสำรองฐานหลักอีกครั้งที่ `data/backups/finishing-cutover-25691116-135346/lthai.dump` ตรวจ SHA-256 ลงอิมเมจเว็บและ API พร้อม migration และล้างเฉพาะ 24 ตารางตามขอบเขตที่อนุมัติ โดยใช้ฐาน `lthai` เดิม

## ชุดใช้งานหลักหลังรวมงานปั๊มกับชาร์ตสี

- เครื่องนี้ใช้ `lthai-docker` ชุดเดียว เว็บ `http://127.0.0.1:3001` และ PostgreSQL ฐาน `lthai` ที่ `127.0.0.1:5434` ใช้ volume เดิม เปิด `web`, `api` และ `pg` ผ่าน `compose.docker.yaml`

- ซ้อมกู้คืนและรวมข้อมูลในฐานแยก จากนั้นเทียบข้อมูลพนักงาน บัญชี ชาร์ตสี และทะเบียนประเภทกระเบื้องในฐานหลักกับต้นทางแล้วตรงกัน `npm run check` ผ่าน และ `npm test` รวม ชุดทดสอบส่งงานข้ามเครื่องเดิม ผ่าน 97 รายการ ไม่มีข้าม Docker build ผ่าน เว็บและ API health ตอบ `200` ส่วน API งานปั๊มและชาร์ตสีปฏิเสธคำขอที่ยังไม่เข้าสู่ระบบ
- ถอด container ทดสอบ 8 ตัวหลังตรวจชุดหลักและกู้ไฟล์สำรองชุดทดสอบกลับเพื่อตรวจว่ามีภาพและประวัติงานปั๊มครบ ไฟล์สำรองก่อนและหลังรวม พร้อมไฟล์จากชุดทดสอบและ SHA-256 อยู่ใน `data/backups/consolidation-*` นอก Git

## ประวัติพัฒนาและทดสอบชาร์ตสีรุ่นแรก

สาขา `codex/color-chart` พัฒนาชาร์ตสีตาม [แบบที่ยืนยัน](superpowers/specs/2026-11-12-color-chart-design.md) และ [แผนพัฒนา](superpowers/plans/2026-11-12-color-chart.md) โค้ดล่าสุดของฟีเจอร์คือ `1182189` เพิ่มเมนูค้นชื่อไทยและอังกฤษ ให้สิทธิ์ดูหรือจัดการผ่านบทบาทเดิม และเก็บภาพตัวอย่างหนึ่งภาพต่อรายการใน PostgreSQL เพื่อให้กู้คืนพร้อมทะเบียนได้

- งานนำเข้าอยู่ใน `scripts/extract-color-chart.py` และ `apps/api/src/color-chart/` หน้าเว็บอยู่ใน `apps/web/src/components/color-chart/` คำสั่งตรวจและนำเข้าอ่าน Excel ซ้ำด้วย `openpyxl==3.1.5` และเทียบกับ JSON โดยตรง รุ่น `d7eecef` ตรวจ Excel จริงด้วย `--preview` ขณะชี้การเชื่อมต่อไปที่ปลายทางที่เข้าไม่ถึง ปฏิเสธ JSON ที่ถูกแก้ นำเข้า 90 ชื่อและ 3 หมายเหตุในฐานทดสอบแยก และข้ามเมื่อรันซ้ำด้วยชุดเดิม
- ตรวจเบราว์เซอร์เดสก์ท็อปและจอกว้าง 390 พิกเซลบน `3afbd6c` ที่ `http://127.0.0.1:3102` ใช้ Docker PostgreSQL พอร์ต `5551` ฐาน `lthai_color_chart_web_qa` เทียบชื่อ ลำดับ และหมายเหตุครบ 90 รายการ ลองค้นไทยและอังกฤษ เพิ่มและแก้ชื่อ อัปโหลด เปลี่ยน ปฏิเสธไฟล์ผิด และลบเฉพาะภาพ บัญชีผู้ดูเปิดภาพได้ บัญชีไม่มีสิทธิ์ชาร์ตสีไม่เห็นเมนู เมนูงานปั๊มและพนักงานเดิมยังเปิดได้
- บน `6f1bc83` รัน `npm run check` และ `npm run build` ผ่าน สร้างอิมเมจ Docker API และเว็บแล้วผ่าน healthcheck รัน `npm test` ด้วย `LTHAI_COLOR_CHART_PYTHON` และชุดทดสอบส่งงานข้ามเครื่องเดิม บน Docker แยก ผ่าน 97 รายการ (legacy 13, API 54, เว็บ 18, ส่งงานข้ามเครื่อง 12) ไม่มีล้มหรือข้าม การแก้หน้าจอหลังลบพร้อมกันใน `1182189` ผ่าน `npm run check` และชุดเว็บ 18 รายการ
- ตรวจเว็บ Docker `1182189` คู่กับ API `6f1bc83` ผ่าน healthcheck และจำลองคำขอที่ล้มในเบราว์เซอร์ โหลดภาพย่อและภาพเต็มซ้ำได้ การลองโหลดทะเบียนใหม่หลังบันทึกชื่อหรือสร้างรายการไม่ส่งคำขอเขียนซ้ำ เมื่อรายการที่เปิดอยู่ถูกลบจากอีกหน้าจอ การโหลดใหม่ปิดรายละเอียดรายการนั้นและยังเพิ่มรายการต่อได้
- ซ้อม `pg_dump` และ `pg_restore` จากฐาน QA ไปยังฐาน `lthai_color_chart_restore_*` แยกใน Docker ตรวจ 91 รายการ (ชื่อจาก Excel 90 และรายการสังเคราะห์ 1) พร้อมภาพสังเคราะห์หนึ่งภาพ ค่าแฮชของแถวใน `public` วิวงานปั๊ม และ sequence ตรงกัน เรียกภาพ WebP จาก API ด้วยบัญชีที่มีสิทธิ์หลังคืนฐานแล้วได้ SHA-256 ตรงกับภาพเดิม
- ตรวจปุ่มยกเลิกและยืนยันลบรายการสังเคราะห์บนมือถือ หลังลบตรวจฐาน QA เหลือ 90 รายการตรงกับ Excel หมายเหตุ 3 รายการ และภาพ 0 รูป เปิดเว็บทดสอบไว้ที่ `http://127.0.0.1:3102`
- วิธีเตรียมและตรวจชุด Excel สำหรับการนำเข้าอยู่ใน [คู่มือเปิดใช้งานชาร์ตสี](color-chart-startup.md) สถานะการเปิดใช้งานเครื่องนี้อยู่ด้านบน

## งานปั๊มรุ่นแรก

- พัฒนาตามแบบที่ยืนยันจาก Excel และคำตอบใน `docs/discovery.md` แล้ว การตรวจรับใช้ข้อมูลสังเคราะห์ใน Docker แยกจากฐานใช้งาน
- ตกลงรุ่นแรกเป็นยอดปั๊ม ของเสีย และสต็อก ค่าแรงเหมาและต้นทุนดินทำภายหลัง
- ระบุประเภทกระเบื้องด้วยขนาดและประเภทดิน แดง ขาว จ้อ หรือสี เพิ่มชื่อเรียกได้
- จำนวนแผ่นคำนวณจากจำนวนไม้เต็ม × แผ่นต่อไม้ของประเภทกระเบื้อง + แผ่นเศษ แยกวันที่ปั๊มกับวันที่พบของเสีย
- ทะเบียนประเภทกระเบื้องเพิ่ม ลบ แก้ไขได้ แต่ละประเภทใช้ไม้เฉพาะและระบุจำนวนวันพัก บรีสปั๊ม รอเซ็ตตัว แล้วเข้าเตาโดยข้ามงานสี
- รับเข้าสต็อกเมื่อบันทึกยอดปั๊ม แสดงกำหนดพัก และลดสต็อกเมื่อยืนยันเบิก เก็บยอดปั๊มเกินตามจริงและให้ผู้รับผิดชอบตัดสินใจเรื่องส่วนเกิน
- ใบสั่งผลิตใช้ได้ทั้งตามออเดอร์ลูกค้าและปั๊มเก็บสต็อก หนึ่งใบรวมยอดได้หลายรายการตามผู้ปั๊มจริง ส่วนสีชุบหรือสีเคลือบระบุในขั้นตอนถัดไป
- ตัดยอดของเสียเมื่อคัดหลังเผาครบและส่งยอด ใช้ผลคัดตามงานเผาเป็นแนวทางเริ่มต้น ระบุผู้ปั๊มเมื่อมีข้อมูลตามกลับได้
- เริ่มด้วยประเภทกระเบื้อง แผ่นต่อไม้ และยอดคงเหลือที่หน้างานยืนยัน ประวัติผลิตย้อนหลังรอข้อมูลเพิ่ม
- ผู้ใช้ยืนยันแบบ `docs/superpowers/specs/2026-11-11-pressing-design.md` แล้ว เหตุผลที่เลือกอยู่ที่ `docs/adr/0002-pressing-traceability.md`
- แผนพัฒนาและวิธีตรวจรับอยู่ที่ `docs/superpowers/plans/2026-11-11-pressing.md` โค้ดอยู่ใน `apps/api/src/pressing/` และ `apps/web/src/components/pressing/` เชื่อมกับสิทธิ์และเมนูเดิม
- รัน `npm test` เปิด ชุดทดสอบส่งงานข้ามเครื่องเดิม บนฐานทดสอบแยก ผ่าน 76 รายการ ไม่มีข้าม `npm run check` และ build ผ่าน ตรวจการสร้างประเภทและใบสั่งบนเดสก์ท็อป ลงยอดและเบิกบนจอมือถือ ตรวจสิทธิ์บัญชีดูอย่างเดียว และกู้คืนข้อมูลสังเคราะห์แล้วเทียบตาราง วิวงานปั๊ม และ sequence ตรงกัน
- ตรวจกรณีเน็ตหลุดด้วย Chromium ว่าการปฏิเสธปิดหน้าต่างยังเก็บคำขอเดิม และการกดลองส่งอีกครั้งใช้ข้อมูลและรหัสเดิม
