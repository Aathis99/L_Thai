# งาน QC ตามใบตรวจสอบคุณภาพ LT-PD-S-01

วันที่: 25 พฤศจิกายน 2026

สถานะ: ร่างตามคำตอบ Q1–Q17 ผ่านการตรวจความพร้อมสำหรับวางแผนแล้ว รอผู้ใช้ตรวจและอนุมัติแบบเต็ม ยังไม่อนุมัติพัฒนา

หลักฐาน: [บันทึกคำถามและคำตอบ](../../qc-discovery.md), [กรอบ ERP](../../erp.md), [คำศัพท์กลาง](../../../GLOSSARY.md), [ADR ขอบเขตใบ QC](../../adr/0007-qc-document-by-firing-product.md)

## เป้าหมายและขอบเขต

คนงานคัดและจดกระดาษตามเดิม ธุรการนำผลมาลงในใบ QC ของงานเตา เติมข้อมูลธุรการ ตรวจยอด และพิมพ์ใบ LT-PD-S-01 ได้ ใช้ผลคัดชุดเดียวกับงานซ่อม จัดสรรออเดอร์ และรับสต็อก ไม่บันทึกผลซ้ำเพื่อทำรายงาน

หนึ่งใบต่อรอบเผา + สินค้า/ดิน/สีเดียวกัน คัดกี่แผ่นหรือกี่ครั้งก็สะสมในใบเดิม งานต่างออเดอร์พิมพ์รวมได้แต่ผลคัดยังแยกต้นทาง เก็บผู้คัดจริงแยกจากผู้บันทึก

รวมหน้ารายการใบ QC หน้าทำงานต่อใบ ร่าง/ยืนยันผลคัดบางส่วน เลขเอกสาร การค้นหา ฉบับพิมพ์ A4 แนวตั้ง และแก้ไขพร้อมประวัติ ปรับแบบกระดาษคนงานกับธุรการให้มีหมวดผลคัดและชื่ออาการตรงกัน โดยการพิมพ์ฉบับทางการในขอบเขตนี้หมายถึงใบธุรการ ไม่บังคับคนงานใช้ระบบดิจิทัล

ไม่รวมระบบอนุมัติแยกคน ลายเซ็นอิเล็กทรอนิกส์ OCR อ่านกระดาษอัตโนมัติ การส่งสินค้าหรือขายครบวงจร ต้นทุน ค่าแรง และการนำเข้าประวัติย้อนหลังทั้งหมด การมีช่องเซ็นบนกระดาษไม่ได้เพิ่มผู้อนุมัติในระบบ

สิ่งที่ถือว่าล้มเหลว: ร่างทำให้เกิดยอดจริง, ยืนยันซ้ำแล้วเพิ่มยอดซ้ำ, รวมใบจนตามออเดอร์ไม่ได้, ยอดออกที่เท่ากับยอดเข้าถูกเข้าใจว่าคัดครบแล้ว, หรือพิมพ์แล้วสร้างสต็อก/งานซ่อมซ้ำ

## แนวทางที่พิจารณาและเลือก

- **A ยึดใบ QC เป็นหลัก — ผู้ใช้เลือก Q16:** เปิดใบของรอบเผาและสินค้า ลงผลแต่ละครั้ง ตรวจยอดสะสมและพิมพ์จากจุดเดียว เหมาะกับธุรการที่รับกระดาษจากหน้างาน ต้องเพิ่มชั้นเอกสารและร่างที่เชื่อมกับผลคัดเดิม
- **B ยึดผลคัดรายครั้ง:** ใช้หน้าลงผลปัจจุบันแล้วเพิ่มหน้ารวม/พิมพ์ เปลี่ยนหน้าทำงานเดิมน้อยกว่า แต่ธุรการต้องสลับจุดทำงานและตรวจหลายรายการก่อนพิมพ์ จึงไม่เลือก

ทั้งสองแนวทางต่อยอดเว็บ/API/PostgreSQL เดิม แนวทางที่เลือกไม่สร้าง ERP อีกชุด

## หน่วยเอกสารและตัวตน

- ใบหนึ่งอ้างรอบเผาที่มี ID จริง ไม่ใช้เพียงเลขเตากับวันที่ เตาเดิมเผารอบใหม่ต้องได้ใบใหม่
- จัดกลุ่มด้วยสินค้า ประเภทการผลิต/ดินรวมสีดินเมื่อมี และสีเคลือบตามตัวตน/ข้อมูลต้นทางที่มีอยู่ งานต่างแบบต่างดินต่างสีไม่รวมกัน ค่าไม่มีสีแยกจากสีที่มี ID
- หลายรายการเข้าเผาที่อยู่กลุ่มเดียวกันรวมใบเดียวได้ แต่แต่ละบรรทัดผลคัดต้องกลับไปหา `loadId` และออเดอร์/งานซ่อมต้นทางได้ ห้ามผูก load เดียวซ้ำหลายใบ
- กลุ่มเดียวกันสร้างพร้อมกันต้องได้ใบเดียวกัน การแก้ชื่อทะเบียนไม่ทำให้เกิดใบใหม่หรือเปลี่ยนประวัติเอกสารเอง ข้อมูลที่ไม่มี identity พอจะพิสูจน์ว่าเหมือนกันต้องไม่รวมด้วยการเทียบชื่ออย่างเดียว
- วันที่ตรวจและรายชื่อผู้คัดเก็บต่อครั้ง ใบรวมแสดงช่วงวันที่ตรวจครั้งแรก–ล่าสุดและรายชื่อไม่ซ้ำ รายละเอียดทุกครั้งยังเปิดดูได้

## เลขที่และออเดอร์

ใช้เลข `QC-2569-000001` เรียงรายปี พ.ศ. ตามวันสร้างใบในเวลาไทย เลขคงเดิมข้ามวัน/ปีเมื่อยังทำใบเดิม ไม่เปลี่ยนเมื่อเพิ่มผลคัด พิมพ์ซ้ำ หรือแก้ไข `LT-PD-S-01` เป็นรหัสแบบฟอร์ม ไม่ใช่เลขใบ

เลขสร้างจากส่วนกลางแบบไม่ชนกัน ไม่ใช้เลขที่ client คำนวณเอง ไม่ใช้เลขเก่าซ้ำ อนุญาตเลขข้ามได้โดยมีประวัติ ไม่ต้องเรียงเลขใหม่หลังยกเลิกร่าง

หัวใบแสดงเลข QC คู่กับเลขอ้างอิงออเดอร์ทุกใบ เช่น `อ้างอิงออเดอร์: OD-001 / OD-002` ตารางรายละเอียดระบุใบสั่งผลิตจริงด้วยเพื่อแยกกรณีเลขอ้างอิงเหมือนกัน งาน OS ไม่มีเลขลูกค้าให้แสดงเลขอ้างอิง OS ที่มีหรือ “งานสั่งเก็บสต็อก #<ID>” ไม่สร้างเลขลูกค้าสมมติ งาน ODP/OSP แสดงประเภทงานและออเดอร์ราก พร้อมอ้างผลคัดเดิมในรายละเอียด

ค้นได้ด้วยเลข QC เลขอ้างอิงออเดอร์ และรหัสใบสั่งผลิต กดเปิดต้นทางได้ตามสิทธิ์ของบัญชี ข้อความหัวเอกสารไม่แทนความสัมพันธ์ของ ID

## ผลคัดและการคำนวณ

งานใหม่มีสี่กลุ่มเท่านั้น:

| กลุ่ม | ความหมาย | ผลหลังยืนยัน |
| --- | --- | --- |
| A+ | ไม่พบอาการเสีย ผ่านด้านคุณภาพ | พร้อมให้จัดสรร/รับสต็อกตามขั้นตอนเดิม |
| เสีย | แผ่นที่คัดเข้าตารางอาการเสีย | นับตามอาการหลัก ไม่สร้างคิวเผาซ้ำจากกลุ่มนี้ |
| ไม่สุก | ต้องนำกลับเข้าเตาใหม่ | เข้าคิวรอเตรียมเผาซ้ำ |
| แต้ม | ต้องแต้มน้ำเคลือบและเข้าเตาใหม่ | เข้าคิวรอเตรียมเผาซ้ำ |

ยกเลิกการกรอก/เลือก A- และ B สำหรับงานใหม่ ไม่เปลี่ยน A-/B เก่าเป็น A+ หรือเสียเอง

จำนวนเข้า = ผลรวมยอดเข้าเผาจริงของรายการที่อยู่ในใบ ดึงจากงานเตา จำนวนออก = จำนวนเข้าอัตโนมัติ ไม่เป็นช่องกรอก และมีคำอธิบาย “อ้างยอดเข้าเตา”

กรอก A+, ไม่สุก และแต้มตามยอดนับจริง กรอกจำนวนของแต่ละอาการเสีย แล้วระบบรวมเป็นยอดเสีย ไม่ต้องกรอกยอดเสียรวมซ้ำ ทุกจำนวนเป็นจำนวนแผ่นเต็มไม่ติดลบ หนึ่งแผ่นอยู่ได้เพียงหนึ่งกลุ่มและหนึ่งอาการเสียหลัก อาการรองเขียนหมายเหตุ

คำนวณต่อรายการเข้าเผาและรวมทั้งใบ:

```text
คัดยืนยันแล้ว = A+ + เสีย + ไม่สุก + แต้ม ของผลที่ยืนยัน
ยังไม่คัด = ยอดเข้าเผาจริง − คัดยืนยันแล้ว
ออกเตา = เข้าเตา (ไม่ใช่ยอดที่คัดแล้ว)
```

ผลยืนยันรวมต้องไม่เกินยอดเข้าของแต่ละ load ร่างแสดงแยกจากผลยืนยัน ไม่ลดตัวเลขยังไม่คัดของยอดจริง แต่ตรวจร่างที่จะยืนยันกับยอดเหลือปัจจุบันเสมอ ห้ามคำนวณ A+ จากยอดเข้าลบเสียระหว่างยังคัดไม่ครบ

ตัวอย่าง: เข้า/ออก 1,000 แผ่น ยืนยัน A+ 500 เสีย 40 ไม่สุก 30 แต้ม 30 รวมคัดแล้ว 600 ยังไม่คัด 400 การมีร่างอีก 100 ไม่เปลี่ยนคัดแล้วเป็น 700 จนกว่าจะยืนยัน

## อาการเสียในสองแบบ

ใช้ชื่อจากสองหน้าต้นฉบับเป็นชุดร่วม: เศษ, มุมเข้า, มุมออก, ฉีกข้าง, อลูมิน่า, งอ, เปิด, แอ่น, หัก, ฉีก, แร่, เศษไม้, รู, กระจก, ดิน, เหล็ก, ร้าวหลัง, ฟอง, เศษชุบ, หยด, ซิลิกอน, หด และไม่สุก

หน้าคนงานและธุรการมีช่อง A+, ไม่สุก, แต้ม และตารางเสียเหมือนกัน ตัด A-/B ออก ชื่ออาการ “ไม่สุก” ในตารางเสียต้องอธิบายว่าเป็นจำนวนที่ตัดสินเป็นเสีย แยกจากช่องไม่สุกที่รอเข้าเตาใหม่ ไม่คัดลอกจำนวนระหว่างสองจุดอัตโนมัติ

แสดงรายการมาตรฐานให้กรอกได้ตรงกับกระดาษ ช่องว่างนับเป็น 0 ในการรวมยอด ไม่บังคับคนกรอกเลข 0 ครบทุกแถว อาการอื่นบันทึกชื่อและจำนวนเพิ่มได้ตามสิทธิ์ QC พร้อมประวัติ การเปลี่ยนชื่อภายหลังไม่เปลี่ยนฉบับเก่า

### ช่องข้อมูลธุรการและเกณฑ์ครบก่อนออกฉบับทางการ

“ส่วนข้อมูลธุรการ” คือการทบทวนส่วนหัวที่ดึงมาและกรอกข้อมูลจากกระดาษตามตารางนี้ ไม่ใช่ชุดช่องเพิ่มเติมที่ผู้พัฒนาต้องเดา:

| ช่องในใบ/ข้อมูลที่ใช้ตรวจ | แหล่งข้อมูลหรือผู้กรอก | จำเป็นก่อนออกทางการ |
| --- | --- | --- |
| รหัสแบบฟอร์ม เลขที่ QC และฉบับเอกสาร | ระบบกำหนด | ต้องมี เลขฉบับสร้างเมื่อออกเอกสาร |
| เตา เบอร์ราง และรอบเผา | งานเตาที่เลือก | ต้องอ้างรอบจริงได้ |
| ชื่อชิ้นงาน/สินค้า แบบผลิต ดินรวมสีดินเมื่อมี และสีเคลือบเมื่อมี | ใบสั่งผลิตและข้อมูลต้นทาง | ต้องครบตามชนิดงาน งานไม่มีสีแสดง “ไม่มีสี” ได้ |
| เลขอ้างอิงออเดอร์/งานสั่งเก็บสต็อก และใบสั่งผลิตแต่ละต้นทาง | ข้อมูลต้นทางหรือ fallback OS ที่กำหนดข้างต้น | ต้องอ้างถึงทุกต้นทางในใบได้ ไม่บังคับเลขลูกค้าให้งาน OS |
| วันที่เข้า วันที่ออก และเวลาเอาของลง | `startedAt`, `withdrawnAt`, `unloadedAt` ของรอบ | ต้องมีและลำดับถูกต้อง แก้ข้อมูลที่ขาดในงานเตา |
| จำนวนเข้าและจำนวนออก | รวมยอดเข้าจริงของ load ในใบ ยอดออกใช้ยอดเดียวกัน | ต้องเป็นแผ่นเต็มมากกว่า 0 และตรงกับต้นทาง |
| วันเวลาตรวจของแต่ละครั้ง | ธุรการกรอกจากกระดาษ ตั้งต้นให้แก้ได้ | ต้องมีสำหรับผลยืนยันทุกครั้ง และไม่ก่อนเอาของลง |
| ผู้คัดจริงของแต่ละครั้ง | ธุรการเลือกพนักงานตามกระดาษ | ต้องมีอย่างน้อยหนึ่งคนต่อครั้งที่ยืนยัน เก็บ ID และชื่อ ณ เวลาทำรายการ |
| A+, ไม่สุก, แต้ม และจำนวนอาการเสีย | ธุรการกรอกจากกระดาษ ยอดเสียรวมอัตโนมัติ | ต้องถูกต้องและคัดยืนยันครบทุก load ไม่มีร่างค้าง |
| ช่วงวันที่ตรวจและรายชื่อผู้คัดในหัวใบรวม | รวมจากผลที่ยืนยัน | ต้องสร้างจากรายละเอียดที่ครบแล้ว ไม่ให้กรอกขัดกับรายละเอียด |
| ผู้บันทึก/ผู้ยืนยันและเวลา | session และประวัติระบบ | ระบบต้องบันทึกได้ ไม่ให้ธุรการพิมพ์แทน session |
| หมายเหตุและอาการรอง | ธุรการกรอกเมื่อมี | ไม่บังคับ |
| ช่องเซ็นผู้รายงาน ผู้ตรวจสอบ ผู้อนุมัติและวันที่ลงนาม | เว้นลงกระดาษ | ไม่บังคับกรอกชื่อ/ลายเซ็นในระบบก่อนพิมพ์ |

ร่างเก็บช่องที่ยังไม่ครบได้ ส่วนปุ่มออกทางการแสดงรายการที่ขาดตามตารางนี้ ช่องต้นทางที่ขาดต้องพาไปแก้ต้นทางตามสิทธิ์ การมีเพียงชื่อผู้บันทึกไม่ทดแทนชื่อคนคัดจริง

## ร่าง การยืนยัน และส่งต่อ

- สร้างใบและเก็บส่วนหัวได้ก่อนมีผลคัด ร่างอาจยังกรอกไม่ครบและแก้/ยกเลิกได้โดยไม่กระทบยอดจริง
- ก่อนยืนยันต้องมีวันเวลาคัด ผู้คัด ต้นทาง และจำนวนถูกต้องอย่างน้อยหนึ่งแผ่น ตรวจว่าทุกบรรทัดอยู่ในใบนี้และยอดไม่เกินต้นทาง ร่างอื่นไม่ใช่การกันของจริง ยืนยันพร้อมกันต้องตรวจยอดล่าสุดใหม่
- การยืนยันครั้งหนึ่งอาจมีหลายบรรทัดต้นทาง แต่ต้องสำเร็จทั้งชุดหรือไม่เปลี่ยนเลย สร้างผล QC เดิมที่เชื่อมกลับร่าง/ใบได้เพียงครั้งเดียว ห้ามมีทางลัดบันทึกผลใหม่ข้ามใบจนยอดในใบไม่ครบ
- ผลยืนยันส่งต่องานได้ทันทีเฉพาะจำนวนที่ยืนยัน ร่างและการพิมพ์ไม่ทำให้เกิดผลคัด งานซ่อม การจัดสรร หรือสต็อก
- A+ ยังต้องผ่านนโยบายเกรดและปลายทางเดิม งานที่ยังไม่กำหนดนโยบายแสดงรอจัดสรร ไม่สร้างสิทธิ์รับเกรดให้ออเดอร์เอง งานตาข่ายยังไม่เป็นยอดพร้อมส่งจนทำตาข่ายครบ
- ไม่สุก/แต้มคงการยืนยันพร้อมเผาบางส่วน จากนั้นใช้แผน/รอบใหม่และกลับมาคัดใหม่ โดยไม่เบิกดินใหม่หรือเพิ่มยอดผลิตใหม่

สถานะใบคำนวณแยกจากสถานะผลคัดแต่ละครั้ง: ร่างเมื่อยังไม่มีผลยืนยัน, กำลังคัดเมื่อยืนยันบางส่วน, คัดครบเมื่อทุก load ครบ, และพร้อมออกฉบับทางการเมื่อคัดครบ ข้อมูลธุรการครบ และไม่มีผลร่างค้าง ร่างที่ซ้ำต้องแก้หรือยกเลิกให้ชัด ไม่ละทิ้งอัตโนมัติ

## ฉบับพิมพ์

พิมพ์ใบธุรการ A4 แนวตั้ง ใกล้ต้นฉบับ มี:

- รหัสแบบฟอร์ม เลข QC และฉบับแก้ไข เลขออเดอร์ทุกใบ เตา/เบอร์/รอบ สินค้า ดิน สี
- วันที่เข้า = วันเริ่มรอบเผา (`startedAt`) วันที่ออก = วันนำเบอร์ออก (`withdrawnAt`) ตามเวลาไทย โดยเอาของลง (`unloadedAt`) ยังคงเป็นเงื่อนไขเริ่ม QC อีกเหตุการณ์หนึ่ง
- วันที่ตรวจเป็นวันเดียวหรือช่วงวันที่ตามผลยืนยัน รายชื่อผู้คัดไม่ซ้ำ ชื่อผู้บันทึกแยกในรายละเอียด
- ยอดเข้า/ออกเท่ากัน ผลคัดสี่กลุ่ม ยอดยังไม่คัด และตารางรายละเอียดเสีย ไม่มี A-/B
- ตารางยอดแยกใบสั่งผลิต/ออเดอร์ และรายละเอียดการคัดแต่ละครั้งเมื่อมีหลายครั้ง
- ช่องเซ็นผู้รายงาน ผู้ตรวจสอบ ผู้อนุมัติพร้อมวันที่ เว้นสำหรับลงบนกระดาษ ไม่บังคับสามบัญชีหรือสามคนต่างกันในระบบ

ถ้ายังไม่ครบ ใช้ข้อความ “ร่าง / ยังไม่คัดครบ” พร้อมยอดรอคัด หากคัดครบแต่ข้อมูลธุรการไม่ครบหรือมีร่างค้างให้พิมพ์เป็นร่างและบอกเหตุผลที่ยังออกทางการไม่ได้

การสร้างฉบับทางการต้องตรวจข้อมูลครบและสร้าง snapshot ของเนื้อหาเอกสารในขณะนั้น เก็บข้อมูลส่วนหัว ชื่อ ออเดอร์ ผลคัด รายละเอียดครั้งที่คัด รูปแบบเอกสาร และผู้สร้าง/เวลา ไม่อ้างชื่อทะเบียนสดให้เปลี่ยนเนื้อหาฉบับเดิมเมื่อเปิดย้อนหลัง

พิมพ์ซ้ำฉบับเดิมใช้ snapshot เดิม ไม่สร้างเลขใหม่หรือเพิ่มยอด และไม่อ้างว่าระบบพิสูจน์ว่าเครื่องพิมพ์พิมพ์สำเร็จ บันทึกได้เพียงการสร้าง/ขอฉบับพิมพ์

หนึ่งใบหมายถึงหนึ่งเอกสาร ไม่จำกัดจำนวนหน้ากระดาษ หน้าแรกแสดงสรุปและอาการเสีย รายละเอียดออเดอร์/ครั้งที่คัดที่ยาวให้ต่อหน้าแนบ ทุกหน้ามีเลข QC ฉบับแก้ไข และหน้า x/y ต้องอ่านง่ายและเห็นเลขอ้างอิงครบ ไม่ย่ออักษรจนอ่านไม่ได้เพื่อบังคับหนึ่งหน้า

## การแก้ไขและสิทธิ์

- ใช้สิทธิ์เดิม `finishing.read` สำหรับอ่าน/พิมพ์, `finishing.qc` สำหรับร่าง/ยืนยันและงาน QC; การแก้ผลยืนยันใช้ `finishing.correct` ร่วมกับสิทธิ์ของส่วนที่กระทบตามเดิม ไม่บังคับผู้อนุมัติใหม่
- แก้ผลยืนยันต้องระบุเหตุผล เก็บก่อน–หลัง ผู้แก้ เวลา รวมวันเวลาคัด ผู้คัด และหมายเหตุที่เป็นข้อมูลเอกสาร ไม่จำกัดเฉพาะจำนวนเหมือนหน้าปัจจุบัน
- ถ้าแก้แล้วกระทบยอดจัดสรร รับสต็อก งานตาข่าย หรือซ่อม/เข้าเผาซ้ำ ต้องตรวจ dependency เดิมทั้งหมด แก้สิ่งที่ระบบเดิมรองรับร่วมกันใน transaction เดียว ถ้ายังย้อนงานปลายทางไม่ได้ให้ปฏิเสธพร้อมรายการที่ต้องแก้ก่อน ไม่ลดหรือเปลี่ยนยอดปลายทางเอง
- ถ้ามีฉบับทางการแล้ว การแก้ที่กระทบเอกสารทำให้ฉบับเดิมเป็นประวัติ ไม่เขียนทับ snapshot เมื่อครบเงื่อนไขจึงออกฉบับใหม่เลข QC เดิม ระบุ “ฉบับแก้ไขครั้งที่ 1” และเพิ่มตามครั้งที่ออกใหม่ พิมพ์ซ้ำโดยไม่แก้ข้อมูลไม่เพิ่มครั้ง
- ถ้าแก้จนไม่ครบ ให้สถานะกลับเป็นกำลังคัด/ร่างตามยอดจริง ฉบับเก่าดูย้อนหลังพร้อมข้อความถูกแทนที่/มีการแก้ไข แต่ห้ามอ้างเป็นฉบับปัจจุบัน
- ข้อมูลเปลี่ยนระหว่างเปิดฟอร์มให้ทบทวน revision ล่าสุด ไม่ทับข้อมูลอีกคนเงียบ ๆ ส่งคำขอซ้ำไม่สร้างผลยืนยัน ใบ หรือฉบับทางการซ้ำ

## ข้อมูลเดิมและการนำขึ้นใช้งาน

นี่เป็นแบบเป้าหมาย ยังไม่มีการแก้โค้ด schema หรือฐานข้อมูลในงานออกแบบ

ข้อเสนอการส่งมอบรุ่นแรก: เส้นทางใบ QC ใหม่ใช้กับรายการที่สร้างด้วยรูปแบบใหม่นี้ ข้อมูลเก่า ผลคัด A-/B นโยบาย สต็อก และต้นทางที่เคยส่งต่อแล้วต้องอ่าน/ตรวจประวัติและใช้ตามกติกาเดิมได้ ไม่ลบ enum ที่อ่านข้อมูลเก่าแล้วพัง ไม่แปลงเกรดเก่าเป็นเกรดอื่นเอง หน้ารายการแยก “ข้อมูลเดิม” ชัด งานที่มีผลคัดเก่าไม่ถูกเอามาคัดซ้ำเพื่อสร้างใบใหม่ การย้ายประวัติเข้ารูปแบบเอกสารใหม่อยู่นอกขอบเขตรุ่นแรก

รายการเข้าเผาที่ยังไม่เคยคัดและมีต้นทางครบอาจเริ่มเอกสารใหม่ได้ โดยต้องหักผลที่มีอยู่จริงเสมอและไม่ผสมผลคัดเก่าที่มี A-/B เข้าใบสี่กลุ่ม หากกลุ่มรอบ/สินค้าใดมีผลเก่าค้างให้คงเส้นทางข้อมูลเดิมจนคัดครบ ไม่แบ่งแผ่นเดิมเข้าเส้นทางใหม่อีกชุด

การเพิ่มผลคัดหลังเปิดใช้ต้องเลือกได้เฉพาะสี่กลุ่มใหม่ทั้งในเส้นทางเอกสารและเส้นทางงานเดิมที่ยังคัดค้างอยู่ เกรด A-/B ที่คงอยู่ใช้สำหรับอ่านประวัติและจัดการผลเดิมตามสิทธิ์ ไม่เปิดให้สร้างผลคัด A-/B ใหม่ผ่านหน้าเดิมหรือ API ทางเดิม การเก็บประวัติเก่าไม่ใช่การคงทางเลือกเกรดที่ผู้ใช้ยกเลิกสำหรับงานใหม่

การพัฒนาภายหลังทำตาม AGENTS.md: สำรอง `lthai` ใน `lthai-docker` สด กู้เข้า QA แยก ตรวจ target ก่อน migration/ทดสอบ ทุก test write อยู่ QA หลังตรวจรับและอนุมัติ code/data จึงสำรองหลักใหม่ ย้ายเฉพาะการเปลี่ยนแปลงและข้อมูลที่อนุมัติ ไม่ restore ทั้ง QA ทับหลัก ตรวจหลักแล้วถอด QA เก็บ backup นอก Git

## เกณฑ์ตรวจรับและข้อเสนอทดสอบ

1. รอบเดียวกันสินค้า/ดิน/สีเดียวกันได้ใบเดียว ต่างรอบ/สินค้า/ดิน/สีแยกใบ ชื่อทะเบียนเปลี่ยนไม่ย้ายกลุ่มย้อนหลัง สร้างพร้อมกันไม่ซ้ำ
2. สองออเดอร์ในใบเดียว ลงผล/อาการเสียแยกตามต้นทาง ค้นเลขแต่ละออเดอร์พบใบนี้และเปิดใบสั่งจริงได้ ยอดปลายทางไม่ไหลข้ามออเดอร์
3. ตัวอย่าง 1,000 แผ่นยืนยัน 600 เหลือ 400 ร่างไม่กระทบยอด เพิ่มครั้งถัดไปได้ ไม่เกินแต่ละ load และยืนยันซ้ำ/พร้อมกันไม่เพิ่มยอดซ้ำ
4. ไม่มี A-/B ในการลงงานใหม่ ยอดเสียเท่ากับอาการหลักรวม อาการรองไม่เพิ่มจำนวน ไม่สุก/แต้มเข้าเผาซ้ำและกลับ QC ได้โดยไม่เพิ่มยอดผลิตหรือสต็อกซ้ำ
5. ยอดออกเท่ากับยอดเข้าและแสดงรอคัดชัด A+ ไม่เกิดจัดสรร/สต็อกเอง ตาข่ายยังใช้กติกาเดิม
6. ฉบับร่างมีเครื่องหมายร่าง ออกทางการไม่ได้ถ้าข้อมูลไม่ครบ มีร่างค้าง หรือยอดไม่ครบ ไม่บังคับกรอกผู้ลงนามกระดาษเป็นผู้อนุมัติในระบบ
7. ฉบับทางการ/พิมพ์ซ้ำคงเนื้อหาเมื่อแก้ทะเบียน ฉบับแก้ไขคงเลข QC และเก็บฉบับเก่า การแก้ที่ย้อน dependency ไม่ได้ถูกปฏิเสธโดยไม่มีผลครึ่งชุด
8. ตรวจสิทธิ์อ่าน/กรอก/แก้/จัดสรร/รับสต็อก รวมการแก้แบบกระทบหลายส่วน การแข่ง revision และคำขอซ้ำ
9. ข้อมูลเดิม A-/B ประวัติและยอดปลายทางไม่เปลี่ยน ไม่รับ load ที่เคยคัดแล้วมาคัดซ้ำ ไม่สร้างนโยบายเกรดจากการ migration เอง
10. render/พิมพ์ A4 ที่มีไทย ชื่อยาว หลายออเดอร์ หลายผู้คัด หลายหน้า และอาการครบทุกแถว ไม่มีข้อความตัดหรือยอดหล่น ตรวจทั้งร่าง/ทางการ/ฉบับแก้ไข
11. ผ่าน typecheck และชุดทดสอบที่เกี่ยวข้อง ตรวจ flow บนเว็บ QA และซ้อมสำรอง/กู้คืนตามคู่มือก่อนนำขึ้นหลัก

## สิ่งที่ผู้พัฒนาตัดสินใจได้ในแผน

ชื่อและโครงตาราง/API การจัดวางองค์ประกอบย่อย การแบ่งไฟล์ การใช้ CSS print หรือ renderer ที่เหมาะกับระบบ การ index และแผน migrate แบบ additive เลือกได้โดยรักษาขอบเขตธุรกิจและข้อมูลเดิม ชื่อโครงสร้างในร่างนี้ไม่บังคับว่าต้องย้าย state ทั้งระบบออกจากโครงเดิม

รายละเอียดผู้ออกแบบที่รอผู้ใช้ตรวจพร้อมแบบเต็ม: ผู้คัดหลายคนต่อครั้ง ช่วงวันที่ตรวจบนใบรวม ตารางอาการแสดงครบและรวมเสียอัตโนมัติ ข้อความแยกไม่สุกที่เสียจากไม่สุกที่เผาซ้ำ วันที่ออกใช้วันนำเบอร์ออก การเก็บ snapshot ฉบับทางการ การต่อหน้าแนบเมื่อข้อมูลยาว และการแยกข้อมูลเดิมออกจากเอกสารรุ่นใหม่

หลังผู้ใช้อนุมัติแบบเต็มจึงจัดทำแผนพัฒนาและเกณฑ์ QA รายงานนี้ไม่ใช่การอนุมัติเริ่มโค้ดหรือนำขึ้นหลัก

## ผลทบทวนแบบ

ผู้รีวิวอ่านอย่างเดียววันที่ 25 พฤศจิกายน 2026 พบว่าคำว่า “ข้อมูลธุรการครบ” ยังไม่แจกแจงช่องบังคับ จึงเพิ่มตารางแหล่งข้อมูล/ผู้กรอก/เกณฑ์ครบจากแบบฟอร์มเดิม ผู้รีวิวตรวจแก้เฉพาะประเด็นนี้แล้วรายงานว่าได้รับคำตอบครบ ไม่มีคำถามสำคัญเดิมค้างอยู่ การตรวจนี้เป็นการทบทวนแบบ ไม่ใช่ผลทดสอบซอฟต์แวร์หรืออนุมัติแทนผู้ใช้
