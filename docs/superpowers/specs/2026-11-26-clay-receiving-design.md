# รับดินเข้า สต็อกวัตถุดิบ และเบิกเข้าโม่

วันที่: 26 พฤศจิกายน 2026

สถานะ: ร่างแบบจากข้อยุติ Q1–Q21 ผ่านการตรวจโดยผู้ตรวจแบบอิสระและได้คำตอบประเด็นที่พบแล้ว รอผู้ใช้อนุมัติเอกสารฉบับนี้ก่อนวางแผนและเริ่มพัฒนา ข้อมูลจำลองใช้ใน QA เท่านั้น การขึ้นหลักยังต้องตรวจรับและยืนยันข้อมูลตาม AGENTS.md

หลักฐาน: [บันทึกคำตอบ](../../clay-receiving-discovery.md), [กรอบ ERP](../../erp.md), [คำศัพท์กลาง](../../../GLOSSARY.md), [ขอบเขตสต็อกวัตถุดิบ](../../adr/0009-raw-clay-stock-by-type.md), [ภาพหลักฐาน](../../adr/0008-clay-receipt-images-in-postgres.md)

## เป้าหมายและขอบเขต

ธุรการลงข้อมูลจากใบชั่งของผู้ขายพร้อมข้อมูลรับดินจริงที่โรงงาน แนบภาพ ยืนยันรับเข้าสต็อกวัตถุดิบ แล้วบันทึกเบิกเป็นกิโลกรัมเข้าเครื่องโม่ได้ ผู้รับดิน ผู้เบิก ผู้บันทึก และผู้ยืนยันเป็นคนละบทบาทซึ่งอาจเป็นคนเดียวกันตามงานจริง

เส้นทางโรงงาน: รับดิน → โม่ → ปั๊มแผ่น → ชุบเคลือบ → เผา → QC ขอบเขตใหม่สิ้นสุดที่การเบิกวัตถุดิบเข้าโม่ ส่วนงานปั๊มเป็นต้นไปใช้ระบบเดิม และคงข้อยกเว้นเส้นทางผลิตเดิม เช่น งานที่ข้ามชุบ

รวมใบรับร่าง/ยืนยัน สต็อกตามประเภทดิน เบิกเข้าโม่ รายการปรับยอด แก้/ยกเลิกพร้อมประวัติ ภาพหลักฐาน ค้นหาและสรุปรับ–เบิกตามช่วงวันที่ ไม่รวมราคา ยอดเงิน VAT เจ้าหนี้ จัดซื้อเต็มระบบ OCR สูตรผสม ผลหลังโม่ แปลงกิโลกรัมเป็นจำนวนแผ่น หรือการตามล็อตถึงกระเบื้องปลายทาง

สิ่งที่ต้องไม่เกิด: ชื่อการค้าทำให้ดินขาวแตกเป็นสต็อกที่เบิกแทนกันไม่ได้, ยืนยันซ้ำเพิ่ม/ลดยอดซ้ำ, ร่างมีผลต่อยอด, แก้ใบรับแล้วประวัติหาย, นำตัวอย่างมาอ้างว่าเป็นคงเหลือจริง หรือเพิ่มสถานะรอยอดตั้งต้นที่ผู้ใช้ปฏิเสธ

## แนวทางที่พิจารณาและเลือก

1. **รวมสต็อกตามประเภทดิน เก็บชื่อการค้าในใบรับ — ผู้ใช้เลือก Q19:** สอดคล้องกับการลงกองแล้วถือเป็นประเภทดินเดียวกัน เบิกดินขาวจากยอดดินขาว ไม่ต้องเลือกชื่อการค้าหรือรถต้นทาง ชื่อและผู้ขายยังค้นในประวัติได้ ความละเอียดในการตามวัตถุดิบถึงเที่ยวรับไม่ใช่คุณสมบัติของรุ่นนี้
2. **แยกสต็อกตามชื่อการค้า — เคยเลือก Q7 แล้วแทนด้วย Q19:** เห็นคงเหลือรายชื่อ แต่ไม่ตรงกับการรวมดินหน้างาน จึงไม่ใช้เป็นตัวตนของยอดคงเหลือ ชื่อยังอยู่ในรายละเอียดรับเข้า
3. **สร้างล็อต สูตรผสม และผลผลิตหลังโม่:** ตามวัตถุดิบละเอียดขึ้น แต่ต้องรู้วิธีวัดและเก็บข้อมูลเพิ่ม ผู้ใช้ยังไม่ทราบวิธีนับเบิกจริงและเลือกจดเป็นกิโลกรัมก่อน จึงไม่สร้างส่วนนี้ล่วงหน้า

ทั้งแนวทางข้อมูลและหน้าจอต่อยอดเว็บ/API/PostgreSQL เดิม ใช้ข้อมูลหลักและบัญชีผู้ใช้ชุดเดียวกับโรงงาน

## ข้อมูลร่วมและเจ้าของข้อมูล

| ข้อมูล | เจ้าของต้นทาง | ใช้และส่งต่ออย่างไร |
| --- | --- | --- |
| ประเภทดินและสีดินเมื่อมี | ทะเบียนดินเดิม/ผู้มีสิทธิ์จัดการทะเบียน | อ้าง ID เดิมเป็นตัวตนสต็อก ไม่เพิ่มประเภทจากชื่อการค้า |
| ผู้รับดิน/ผู้เบิกจริง | ทะเบียนพนักงานเดิมและผู้รับผิดชอบหน้างาน | เลือก ID และเก็บชื่อ ณ เวลายืนยัน แก้ชื่อทะเบียนไม่เปลี่ยนเอกสารเก่า |
| ผู้บันทึก/ยืนยัน/แก้ | บัญชีผู้ใช้และสิทธิ์เดิม | อ่านจาก session และประวัติ ไม่เดาจากผู้รับดิน |
| ใบชั่ง เลขบิล ผู้ขาย ชื่อดิน ทะเบียนรถ | เอกสารผู้ขาย; ธุรการเป็นผู้ลงและตรวจข้อมูล | เก็บเป็นข้อมูล ณ เวลารับ ไม่สร้างทะเบียนผู้ขายหรือบัญชีเจ้าหนี้ใหม่ในรุ่นนี้ |
| วันเวลารับดินที่โรงงาน | ผู้รับดินจริง/ธุรการผู้บันทึก | แยกจากเวลาชั่งต้นทางและเวลาลงระบบ |
| ใบรับ/ใบเบิก/ปรับยอดที่ยืนยัน | โมดูลรับดินและผู้ได้รับสิทธิ์ | เป็นหลักฐานการเพิ่ม–ลดสต็อกวัตถุดิบ |
| งานปั๊มและสต็อกแผ่น | โมดูลงานปั๊มเดิม | ไม่หักวัตถุดิบจากจำนวนแผ่น และไม่สร้างรายการปั๊มอัตโนมัติเมื่อเบิกเข้าโม่ |

ยังไม่ทราบชื่อแผนกของผู้รับดิน ไม่สร้างชื่อแผนกสมมติเป็นเงื่อนไขใช้งาน ใช้บทบาทผู้รับจริงและสิทธิ์บัญชีตามที่ตกลงก่อน ผู้มีสิทธิ์บันทึกและยืนยันเป็นบัญชีเดียวกันได้ ไม่เพิ่มชั้นอนุมัติอีกคน

## ใบรับดิน

หนึ่งใบรับแทนรถหนึ่งเที่ยวและชื่อดินหนึ่งชื่อ ใช้ชื่อการค้าตามใบ เช่น DKL-325PD พร้อมเลือกประเภทดินที่รับจริง เช่น ดินขาว การรับชื่ออื่นที่เป็นดินขาวเพิ่มยอดดินขาวเดียวกัน

ข้อมูลในใบรับ:

- เลขใบรับของระบบ ผู้ขาย เลขที่บิล/ใบชั่ง วันที่ในเอกสาร ชื่อดินตามบิล และประเภทดิน
- ทะเบียนรถในเหตุการณ์ชั่งเข้าและชั่งออก ให้คัดค่าเดียวกันได้ แต่เก็บได้ทั้งสองช่องตามเอกสาร
- วันเวลาชั่งเข้า ณ ผู้ขาย: ก่อนใส่ดิน พร้อมน้ำหนักรถก่อนใส่ดิน
- วันเวลาชั่งออก ณ ผู้ขาย: หลังใส่ดิน พร้อมน้ำหนักรถและดินก่อนออกส่ง
- น้ำหนักสุทธิจากใบชั่ง และค่าที่คำนวณจากน้ำหนักสองฝั่งเมื่อมีข้อมูลครบ
- วันเวลาที่โรงงานรับดิน ผู้รับจริง หมายเหตุ และภาพหลักฐาน
- ผู้สร้าง/บันทึก/ยืนยัน/แก้กับเวลาที่ระบบทำรายการ เก็บอัตโนมัติแยกจากวันเวลาหน้างาน

**การเลือกเติมของผู้พัฒนา:** เลขใบรับอัตโนมัติรายปี เช่น `RC-2569-000001` ไม่ให้เลขบิลเป็น ID เอกสาร เลขบิลของผู้ขายต่างรายอาจซ้ำกัน เตือนรายการซ้ำเมื่อผู้ขาย+เลขบิล+วันที่+ทะเบียนรถตรงกัน ให้ตรวจรายการเดิมก่อน โดยไม่เดาว่าเลขบิลเดียวใช้กับหลายเที่ยวไม่ได้

สถานะ `ร่าง → ยืนยัน → ยกเลิก`:

- ร่างบันทึกข้อมูลบางส่วนและรูป 0–3 รูปได้ ยังไม่เพิ่มยอด
- ยืนยันต้องมีประเภทดิน ชื่อดิน ผู้ขาย เลขที่/วันที่เอกสาร น้ำหนักสุทธิเป็นบวก วันเวลารับจริง ผู้รับ และรูป 1–3 รูป
- คัดข้อมูลชั่งจากเอกสารตามจริง เวลา/น้ำหนักแต่ละฝั่งและทะเบียนรถที่เอกสารไม่ระบุให้เว้นพร้อมหมายเหตุข้อมูลขาด ไม่เติมค่าที่เดาเป็นข้อเท็จจริง อนุญาตยืนยันเอกสารที่มีข้อมูลชั่งเพียงฝั่งเดียวเมื่อข้อมูลบังคับข้างต้นครบ โดยไม่คำนวณ/ตรวจคู่ที่ยังขาด ตรวจความสัมพันธ์ของเวลาและสูตรน้ำหนักเฉพาะเมื่อมีค่าที่ต้องใช้ครบ
- เมื่อมีเวลาชั่งครบ ชั่งออกต้องไม่ก่อนชั่งเข้า และวันเวลารับโรงงานต้องไม่ก่อนชั่งออก บันทึกวันเต็มรองรับข้ามวัน
- คำนวณสุทธิจาก **น้ำหนักรถพร้อมดิน − น้ำหนักรถก่อนใส่ดิน** ทั้งสองค่าเป็นบวกและรถพร้อมดินต้องมากกว่า ค่าสุทธิที่กรอกตามใบต้องตรงกับผลต่างตามความละเอียดที่ระบบรับ หากไม่ตรงคงร่างไว้ให้ตรวจเอกสาร
- ยืนยันสำเร็จครั้งเดียวจึงเพิ่มยอดสต็อก การส่งคำขอเดิมซ้ำต้องได้ผลเดิม

กติกาเว้นข้อมูลที่เอกสารขาดและเลขเอกสารข้างต้นเป็นข้อเลือกเติมในร่างแบบเพื่อให้ใช้กับเอกสารที่ข้อมูลไม่ครบได้ ไม่ได้อ้างว่าผู้ใช้เคยยืนยันรายละเอียดนี้

## น้ำหนัก วันเวลา และตัวตนสต็อก

เก็บน้ำหนักเป็นกิโลกรัมแบบทศนิยมที่คำนวณได้ตรง เลือกความละเอียดสามตำแหน่งกิโลกรัมในรุ่นนี้ กรอกหน่วยกิโลกรัมหรือแปลงจากตันได้ด้วย 1 ตัน = 1,000 กิโลกรัม แสดงกิโลกรัมพร้อมค่าตันเมื่อถึง 1,000 กิโลกรัม โดยไม่แปลงหรือปัดทิ้งในประวัติ

ใช้ `clay_type_id` เดิมเป็นตัวตนหลัก ดินขาวหลายชื่อรวมยอดเดียวกัน ชื่อการค้า ผู้ขาย และทะเบียนรถไม่เป็นตัวแยกยอด หากรับดินสี ต้องรักษาเอกลักษณ์สีดินตามทะเบียนเดิมด้วย `clay_color_id` และแยกยอดสีต่างกันตามคำศัพท์เดิม ไม่รวมดินสีทุกสีเป็นกองเดียว ตัวอย่าง QA ครั้งนี้มีเฉพาะดินขาว ไม่เพิ่มดินสี/สีดินสมมติให้โรงงาน

เวลาหน้างานใช้วันเวลาไทยแบบ 24 ชั่วโมงตามฟอร์มเดิม ชั่วโมง 00–23 นาที 00–59 ส่งค่า ISO พร้อมเขตเวลา `+07:00` เวลาที่ลงระบบเป็นเวลาจากเซิร์ฟเวอร์ บันทึกย้อนหลังได้ตามเหตุการณ์จริง

## สต็อก เบิกเข้าโม่ และปรับยอด

ยอดคงเหลือคำนวณตามลำดับรายการยืนยัน: รับเข้าเพิ่ม เบิกลด และเมื่อถึงรายการตรวจนับให้ยึดยอดที่ตรวจนับจริงเป็นยอด ณ จุดนั้น ผลต่างของรายการปรับยอดเป็นค่าที่คำนวณจากยอดก่อนจุดตรวจนับ ไม่ใช่ค่าคงที่ที่ตรึงไว้ตลอด ร่างไม่รวมในยอด ไม่มีระบบรอยอดตั้งต้น

เบิกเข้าโม่ระบุประเภทดิน (และสีดินเมื่อเกี่ยวข้อง) จำนวนกิโลกรัม วันเวลา ผู้เบิกจริง และหมายเหตุ ผู้ใช้ยังไม่ทราบวิธีวัดหน้างาน จึงให้กรอกตัวเลขกิโลกรัมเอง ไม่แปลงจากถัง/กระสอบ/บุ้งกี๋และไม่อ้างว่าชั่งจริงโดยอัตโนมัติ ไม่บังคับเลือกชื่อการค้า เที่ยวรถ ล็อต ใบสั่งปั๊ม หรือสินค้า

**การเลือกเติมของผู้พัฒนา:** ใบเบิกมีร่าง/ยืนยัน/ยกเลิกเช่นเดียวกับใบรับ ลดยอดเมื่อยืนยัน มีเลขเบิกอัตโนมัติ และป้องกันเบิกเกินคงเหลือที่ระบบมี การยืนยันเบิกไม่สร้างสต็อกหลังโม่ ไม่สร้างงานปั๊ม และไม่ส่งยอดแผ่นไปขั้นชุบหรือเตา

รายการปรับยอดเลือกประเภทดิน ระบุยอดคงเหลือใหม่ที่ตรวจนับ ผู้ตรวจนับ และเหตุผล ระบบคำนวณผลต่างจากยอดปัจจุบันขณะยืนยัน แล้วบันทึกยอดก่อน–หลัง ค่าตรวจนับที่ยืนยัน และผู้ยืนยัน แสดงในประวัติการเคลื่อนไหว แยกจากใบรับตามบิล

**Q21 ผู้ใช้ยืนยัน:** ยอดตรวจนับเป็นข้อเท็จจริง ณ วันเวลานั้น เมื่อแก้/ยกเลิกหรือเพิ่มเอกสารย้อนหลังที่เกิดก่อนจุดตรวจนับ ให้คำนวณยอดก่อนจุดนั้นและผลต่างปรับใหม่ โดยคงค่าตรวจนับที่ยืนยันเดิม และเก็บประวัติผลคำนวณก่อน–หลังผูกกับรายการที่เป็นสาเหตุ ตัวอย่างรับ 100 → เบิก 20 → ตรวจนับ 50 มีผลปรับ −30 ต่อมาแก้รับเก่าเป็น 120 ผลปรับจะเป็น −50 แต่คงเหลือหลังตรวจนับยังเป็น 50 รายการรับ/เบิกหลังจุดนั้นยังเพิ่ม–ลดตามปกติ

หากมีหลายจุดตรวจนับ ให้คำนวณตามลำดับถึงทุกจุดที่ได้รับผล โดยคงค่าตรวจนับของแต่ละจุด ไม่แก้เหตุผล ผู้ตรวจนับ หรือเวลาเดิมอัตโนมัติ รายงานย้อนหลังแสดงผลที่คำนวณตามข้อมูลฉบับปัจจุบัน พร้อมเปิดประวัติค่า/ผลก่อนแก้ได้ หากแก้หรือยกเลิกรายการตรวจนับเองต้องใช้สิทธิ์ปรับยอดพร้อมเหตุผล และคำนวณรายการถัดไปใหม่ตามกติกาเดียวกัน

**การเลือกเติมของผู้พัฒนา:** รุ่นนี้ปรับยอดปัจจุบัน ณ เวลายืนยัน ไม่ตั้งยอดนับย้อนหลัง ส่วนการแก้วันเวลาหรือจำนวนในเอกสารรับ/เบิกเก่าทำผ่านฉบับแก้ไข การคืนวัตถุดิบที่ยังไม่โม่ใช้รายการเพิ่มยอดพร้อมเหตุผลและอ้างใบเบิกเดิมในหมายเหตุ ไม่สร้างระบบสต็อกดินหลังโม่หรือสูตรแปลงสภาพเพื่อรองรับการคืน

## แก้ไข ยกเลิก และความถูกต้องของยอด

- แก้ร่างได้ตามสิทธิ์บันทึก แก้/ยกเลิกรายการยืนยันแล้วต้องมีสิทธิ์แก้ไขและเหตุผล
- เก็บค่าก่อน–หลัง ผู้แก้ เวลา และเลขฉบับเดิมเปิดย้อนหลังได้ การเปลี่ยนประเภทดินต้องปรับผลต่อทั้งยอดเก่าและยอดใหม่
- ไม่ลบใบที่ยืนยันและผลต่อยอดทิ้ง การยกเลิกเก็บสถานะและสร้างผลกลับยอดที่ตรวจสอบได้ ยกเลิกซ้ำไม่กลับยอดซ้ำ
- ใบรับที่เบิกต่อแล้วแก้ได้เมื่อยอดหลังปรับยังถูกต้อง ตรวจรายการยืนยันตามวันเวลาหน้างานและลำดับคงที่เมื่อเวลาเท่ากัน โดยคำนวณจุดตรวจนับตาม Q21 หากการแก้ทำให้ยอดติดลบในประวัติหรือปัจจุบัน ให้ปฏิเสธทั้งรายการพร้อมเหตุผล และเก็บค่าที่ผู้ใช้กรอกไว้ตรวจแก้
- ล็อกยอดประเภทดินที่เกี่ยวข้องใน transaction เดียวกันและเรียงลำดับล็อกคงที่เมื่อแก้ข้ามประเภท เพื่อให้สองคนเบิกพร้อมกันไม่ผ่านเกินยอด
- ใช้ revision ป้องกันหน้าจอเก่าเขียนทับ และรหัสคำขอป้องกันบันทึกซ้ำ การเปลี่ยนเอกสาร ภาพ ประวัติ ผลยอด และการคำนวณผลปรับใหม่ของจุดตรวจนับที่เกี่ยวข้องต้องสำเร็จหรือยกเลิกด้วยกัน

กติกาความถูกต้องด้าน transaction, revision และยอดไม่ติดลบเป็นข้อเลือกเติมของผู้พัฒนาเพื่อทำให้ข้อยุติ Q18/Q20 ใช้งานได้ ไม่ใช่การเพิ่มขั้นอนุมัติ

## ภาพหลักฐานและความเร็ว

ใบรับยืนยันแล้วต้องมีภาพ 1–3 รูป ไม่บังคับว่ารูปใดต้องเป็นบิล ใช้ได้ทั้งบิล/ใบชั่งและภาพรับดิน รูปทั้งหมดเก็บใน PostgreSQL ตาม ADR 0008 โดยตรวจสิทธิ์ก่อนอ่านและแก้

**การเลือกเติมของผู้พัฒนาในร่างแบบ:** รองรับ JPEG/PNG/WebP รูปนิ่ง อัปโหลดไม่เกิน 8 MiB ต่อรูปและจำกัดจำนวนพิกเซลตามตัวจัดการภาพเดิม หมุนตาม EXIF แล้วแปลง WebP ก่อนจัดเก็บ เป้าหมายด้านยาวไม่เกิน 2,560 พิกเซลและภาพเก็บไม่เกิน 1 MiB ต่อรูป ต้องตรวจการขยายอ่านเลขเอกสารและน้ำหนัก หากไม่สามารถทำให้ผ่านขนาดและอ่านได้ ให้แจ้งเลือกภาพใหม่ ไม่บีบจนข้อความอ่านไม่ได้

เก็บเฉพาะภาพที่แปลงแล้วในฐานข้อมูล ไม่เก็บไฟล์ต้นฉบับขนาดใหญ่ซ้ำถาวร ข้อนี้เป็นข้อเลือกเติมของผู้พัฒนาที่ต้องให้ผู้ใช้เห็นขณะตรวจแบบ แสดงจำนวนรูปในหน้ารายการและโหลดภาพเฉพาะเมื่อเปิดดู ห้ามส่งภาพไบนารีหรือ Base64 ทั้งหมดไปกับตารางสต็อก แบ่งหน้ารายการและค้นหาฝั่งเซิร์ฟเวอร์

แก้/เปลี่ยนภาพหลังยืนยันต้องมีเหตุผลและเก็บประวัติ รวมถึงภาพของฉบับเดิมที่ยังเป็นหลักฐานย้อนหลัง นับ 1–3 รูปต่อฉบับ มีการอ้างอิงภาพเดิมซ้ำได้โดยไม่ทำสำเนาไบต์ทุกครั้ง ห้ามทำให้ฉบับที่ยืนยันเหลือภาพศูนย์รูปหรือทำให้ภาพฉบับเก่าหายไป

## หน้าจอที่ใช้ทำงาน

เพิ่มทางเข้า “รับดินและวัตถุดิบ” ในพื้นที่ทำงานเดิม แยกจากสต็อกแผ่นดินปั๊ม มีสี่หน้าทำงานซึ่งค้นและเปิดรายการต้นทางได้:

```text
รับดินและวัตถุดิบ
  รับเข้า: วันที่รับ | เลขใบรับ | ผู้ขาย | ชื่อในบิล | ประเภทดิน | สุทธิ | สถานะ | รูป
  สต็อก: ประเภทดิน/สีดิน | รับเข้า | เบิกเข้าโม่ | ปรับยอด | คงเหลือ
  เบิกเข้าโม่: วันเวลา | ประเภทดิน | กิโลกรัม | ผู้เบิก | สถานะ
  ปรับยอดและประวัติ: วันเวลา | รายการอ้างอิง | ก่อน | เปลี่ยนแปลง | หลัง | เหตุผล
```

กรองตามช่วงวันที่ ประเภทดิน สถานะ ผู้ขาย/เลขบิล/ทะเบียนรถตามหน้าที่เกี่ยวข้อง เปิดรายละเอียดและประวัติจากแถว มีปุ่มเพิ่มรับเข้า เบิก และปรับยอดตามสิทธิ์ สรุปช่วงวันที่ต้องแยกยอดยกมา/เคลื่อนไหวในช่วง/คงเหลือปลายช่วงให้ถูกต้อง ไม่เอาเฉพาะยอดในช่วงมาเรียกคงเหลือทั้งหมด

หน้ารับแบ่งข้อมูลบิล ชั่งเข้าผู้ขาย ชั่งออกผู้ขาย รับที่โรงงาน และภาพ เพื่อให้เวลาเข้า/ออกไม่สับสนกับเวลามาถึงโรงงาน ใช้รูปแบบตารางและฟอร์มเดิมของแอป ข้อผิดพลาดแสดงสาเหตุและคงค่าที่กรอกไว้

## สิทธิ์และโครงข้อมูลที่ผู้พัฒนาเลือกเติม

เพิ่มสิทธิ์เฉพาะโมดูลสำหรับดูข้อมูล บันทึกรับ/เบิก ยืนยัน แก้/ยกเลิก และปรับยอด โดยใช้ระบบบัญชี/บทบาทเดิม ผู้ดูแลระบบได้รับสิทธิ์โมดูลใหม่ ผู้ใช้บทบาทอื่นไม่ถูกเพิ่มสิทธิ์เอง ผู้บันทึกกับผู้ยืนยันเป็นบัญชีเดียวกันได้เมื่อมีสิทธิ์ครบ สิทธิ์ดูครอบคลุมประวัติและภาพที่เกี่ยวข้อง ไม่มี URL ภาพสาธารณะข้ามการตรวจสิทธิ์

แยกโมดูล API สำหรับวัตถุดิบจาก `pressing` ซึ่งนับแผ่น เพิ่มตารางเอกสารรับ/เบิก/ปรับยอด รูปและฉบับแก้ไข พร้อมรายการเคลื่อนไหวน้ำหนักที่อ้างเอกสารต้นทาง ไม่ต้องเปลี่ยน ID หรือ schema ของใบสั่ง/แผ่นดินปั๊มเดิม ใช้ migration แบบเพิ่มโครงสร้างและรันซ้ำได้ รหัสตาราง/route และวิธีจัดหน้าฟอร์มเป็นรายละเอียดในแผนพัฒนา

## ข้อมูลจำลองและ QA

เตรียมต้นทางจาก Markdown ที่ผู้ใช้ระบุไว้ใน `.qa/clay-receiving/source-preview.json` นอก Git นำเฉพาะหกแถวดินขาว ตัดแถวทราย ไม่เอาราคา/VAT และไม่อ้างว่ารับสะสมเท่ากับคงเหลือจริงของโรงงาน ไฟล์นี้เป็นข้อมูลสำหรับสร้างตัวอย่าง ยังไม่มีการเขียนฐานข้อมูล

ใน QA ใช้ชื่อ/จำนวน/วันที่เอกสารต้นทางที่มีจริง และเติมข้อมูลที่ขาด เช่น เวลาชั่ง น้ำหนักรถ ทะเบียนรถ ผู้รับ และภาพ ด้วยข้อมูลจำลองที่ระบุชัดในชุดตัวอย่างและหน้ารายละเอียด ไม่สร้างภาพบิลปลอมที่ดูเป็นเอกสารจริง ใช้ภาพมีข้อความตัวอย่างสำหรับทดสอบภาพ 1–3 รูป ตัวเลขน้ำหนักรวมที่จำลองต้องสัมพันธ์กับสุทธิจากต้นทาง

ทดสอบรับจากชื่อการค้าต่างกันแล้วรวมประเภทดินเดียวกัน เบิกเข้าโม่ ปรับยอด และแก้/ยกเลิกครบวงจร ผู้ใช้แก้ข้อมูลจำลองใน QA ได้พร้อมประวัติ ตัวอย่าง QA ไม่ถูกเลือกย้ายขึ้นหลักโดยอัตโนมัติ ไม่มีโหมดรอยอดตั้งต้นในหน้าผลิตภัณฑ์

ขั้นดำเนินการหลังอนุมัติแบบ:

1. สำรองฐาน `lthai` สดจาก `lthai-docker` ตรวจ archive/checksum ตามคู่มือ Docker กู้เป็นฐาน QA แยก ยืนยันชื่อฐาน/role/ปลายทางก่อน migration หรือทดสอบเขียน
2. ใช้ QA stack แยกพอร์ตและ credentials นอก Git ไม่กระทบเว็บหลัก 3001/ฐานหลัก 5434 รัน migration สองครั้งและตรวจว่าเอกสาร/ข้อมูลหลักเดิมไม่เปลี่ยน
3. ทดสอบโมดูลและตัวอย่างจนผู้ใช้ตรวจรับ แล้วให้ยืนยัน code/migration และข้อมูลที่จะเก็บก่อนนำขึ้นหลัก สำรองหลักสดอีกครั้ง ย้ายเฉพาะรายการที่อนุมัติ รักษาการเปลี่ยนแปลงที่เกิดหลังสำเนา QA ไม่ restore QA ทับหลัก
4. ตรวจระบบจริงและผลยอด แล้วถอด QA containers/ฐานของโมดูลตาม AGENTS.md เก็บ backups ไว้และเหลือ `lthai-docker` เป็น stack LThai เดียว

ก่อนขึ้นหลักต้องยืนยันค่าตั้งต้นจริงหรือชุดข้อมูลที่ผู้ใช้เลือกเก็บ การยืนยันให้ใช้ตัวอย่างเพื่อทดสอบครั้งนี้ไม่ใช่การยืนยันค่าตั้งต้นจริง

## เกณฑ์ตรวจรับ

- รับหนึ่งเที่ยวตามบิล แยกเวลาชั่งเข้า/ออกต้นทาง เวลารับโรงงาน และเวลาบันทึกได้ ตรวจข้ามวันและสูตรน้ำหนักถูกต้อง
- ร่างไม่เพิ่มยอด รูปศูนย์/เกินสามยืนยันไม่ได้ ภาพบีบอัดอ่านได้และโหลดตามสิทธิ์เมื่อเปิดดู
- รับดินขาวต่างชื่อแล้วรวมยอดดินขาว เบิกจากประเภทเดียวกันเป็นกิโลกรัม ลดครั้งเดียว ไม่เปลี่ยนสต็อกแผ่นหรือสร้างงานปั๊ม
- ปรับยอดคงเหลือจริงด้วยเอกสารปรับยอดและเหตุผล เปิดใบรับเดิมแล้วค่ายังตรงประวัติ แก้ข้อมูลรับผิดใช้ฉบับแก้ไขได้ กรณีรับ 100/เบิก 20/ตรวจนับ 50 แล้วแก้รับเป็น 120 ต้องยังคงเหลือ 50 โดยผลปรับเปลี่ยนจาก −30 เป็น −50 พร้อมประวัติ ทดสอบหลายจุดตรวจนับและรายการหลังตรวจนับด้วย
- ยืนยัน/ยกเลิกซ้ำ สองคนเบิกพร้อมกัน หน้าจอเก่า และแก้ข้ามประเภทไม่ทำให้ยอดหรือประวัติผิด หากรายการใดถูกปฏิเสธต้องไม่มีภาพ/ยอด/ประวัติที่เขียนค้างบางส่วน
- แก้/ยกเลิกรับที่มีเบิกต่อแล้วตรวจผลต่อยอดในอดีตและปัจจุบันได้ ห้ามทำให้ยอดติดลบ และบอกเหตุผลให้ผู้ใช้แก้ได้
- ตรวจ permissions ทั้ง API และหน้าจอ ประวัติแสดงผู้รับ/ผู้เบิกจริงแยกบัญชีผู้บันทึก ชื่อเก่าและภาพเก่ายังอ่านได้หลังแก้ทะเบียนหรือเอกสาร
- ตัวอย่าง QA มาจากแถวที่เลือกและตัดทราย มีการระบุข้อมูลเติมจำลองชัด ตรวจยอดรวมอิสระก่อน–หลังแต่ละขั้น ไม่มีข้อมูลส่วนตัวหรือ credentials เข้า Git

## สถานะอนุมัติ

Q1–Q21 เป็นข้อยุติจากการสัมภาษณ์ โดย Q19 แทนกติกาแยกสต็อกตามชื่อใน Q7 และ Q16 แทนข้อเสนอระบบรอยอดตั้งต้น ผู้ใช้ตอบ Q21 ที่พบจากการตรวจแบบแล้ว ส่วนใบชั่งข้อมูลฝั่งเดียวอนุญาตกรอกเท่าที่มีพร้อมหมายเหตุเมื่อข้อมูลบังคับครบ โดยระบุเป็นข้อเลือกเติมของผู้พัฒนา รอผู้ใช้ตรวจและอนุมัติเอกสารฉบับนี้ก่อนวางแผนและเริ่มพัฒนา
