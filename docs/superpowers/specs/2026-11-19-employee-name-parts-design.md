# แยกส่วนชื่อพนักงานและปรับทะเบียนปี 2569

สถานะ: ผู้ใช้ตรวจรับ QA และอนุมัตินำขึ้นฐานหลักเมื่อ 19 พฤศจิกายน 2026; เปิดใช้บน lthai-docker แล้ว
วันที่: 19 พฤศจิกายน 2026

## เป้าหมายและขอบเขต

เก็บคำนำหน้า ชื่อ และนามสกุลของพนักงานแยกกัน แก้ฟอร์มเพิ่ม/แก้ไขและทุกส่วนที่ใช้ชื่อพนักงาน แล้วนำเข้าข้อมูลทะเบียนปี 2569 ที่ผู้ใช้เลือก โดยรักษาพนักงาน ประวัติการทำงาน และความเชื่อมโยงเดิม

แหล่งข้อมูลเป็นไฟล์ส่วนตัวนอก Git: Excel ต้นฉบับชีต `พนักงาน ปี2569` และ Markdown ที่เลือก B/C/D/G/H ข้อมูลจริง เลขประจำตัว staging และ backups ต้องอยู่นอก Git ไม่แนบในเอกสารนี้

## ทางเลือกและสิ่งที่ผู้ใช้ยืนยันแล้ว

- A: เพิ่มสามช่องและเก็บ `employees.name` เป็นชื่อรวมที่ดูแลให้ตรงกัน กระทบน้อยกว่าแต่มีข้อมูลชื่อซ้ำให้ควบคุม
- B: เลิกเก็บ `employees.name` ใช้สามช่องเป็นข้อมูลหลัก และแก้ทุกส่วนให้ประกอบชื่อเมื่อต้องแสดง ผู้ใช้เลือก **B**
- คำนำหน้าเลือก นาย/นาง/นางสาว หรืออื่น ๆ กรอกเองได้ และเว้นว่างได้
- ชื่อจำเป็น นามสกุลเว้นว่างได้ แต่ละช่องรองรับหลายคำและภาษาต่างประเทศ
- เพิ่มคนที่ยังไม่มี แก้คนเดิม เก็บคนที่อยู่นอกไฟล์ และไม่ใช้ช่องว่างต้นทางล้างค่าเดิม
- คืนศูนย์นำหน้า 8 ช่องตามรูปแบบแสดงผลใน Excel ใช้เลขจากไฟล์แทนค่าทดสอบที่ขัดกันหนึ่งคน และแก้คำนำหน้าที่สะกดผิดเป็นนางสาว

## โครงสร้างและกติกาข้อมูล

`employees` เก็บ `prefix`, `first_name`, `last_name` เป็นข้อความ และไม่มีคอลัมน์ `name` หลังย้ายเสร็จ ไม่สร้างคอลัมน์ชื่อรวมใหม่มาทดแทน

- `prefix`: ไม่เป็น NULL ค่าเริ่มต้นว่าง สูงสุด 40 ตัวอักษร ไม่จำกัด enum ที่ฐานเพื่อรองรับคำนำหน้าอื่น
- `first_name`: ไม่เป็น NULL ต้องมีข้อความหลัง trim สูงสุด 120 ตัวอักษร
- `last_name`: ไม่เป็น NULL ค่าเริ่มต้นว่าง สูงสุด 120 ตัวอักษร
- trim ขอบและยุบช่องว่างติดกันเป็นช่องเดียว แต่ไม่ตัดคำภายในชื่อ ไม่บังคับอักษรไทย ไม่บังคับเปลี่ยนตัวพิมพ์
- ชื่อซ้ำกันได้ ใช้ id และรหัสพนักงานเป็นตัวอ้างอิงเดิม ไม่เพิ่มข้อจำกัดชื่อไม่ซ้ำ
- เลขประกันสังคมและเลขผู้เสียภาษีเก็บเป็นข้อความเช่นเดิม ว่างได้ เมื่อมีค่าต้องเป็นเลข ASCII ครบ 13 หลัก เก็บศูนย์นำหน้า ไม่เพิ่ม checksum validation

ข้อเสนอรายละเอียดเพื่อให้อนุมัติพร้อมแบบ: ชื่อแสดงผลนำส่วนที่ไม่ว่างมาต่อด้วยช่องว่างหนึ่งตัว เช่นชื่อสมมติ `นาย สมชาย ใจดี` และชื่อเดี่ยวไม่มีช่องว่างเกิน หน้าเว็บและ API ใช้กติกาเดียวกัน

## ฟอร์มและหน้าจอ

แทนช่องชื่อรวมในทั้งเพิ่มและแก้ไขด้วยคำนำหน้า/ชื่อ/นามสกุล ใช้ชุดฟอร์มเดิม รักษารหัส แผนก ตำแหน่ง โทรศัพท์ เลขประจำตัว และสถานะเดิม

คำนำหน้าเริ่มว่าง มี นาย/นาง/นางสาว/อื่น ๆ เมื่อเลือกอื่น ๆ แสดงช่องข้อความและบังคับข้อความสำหรับตัวเลือกนั้น ค่าที่เก็บเป็นข้อความจริง ไม่เก็บคำว่า “อื่น ๆ” แทนคำนำหน้า เปิดแก้ไขค่าที่ไม่ใช่ตัวเลือกมาตรฐานได้โดยไม่สูญเสียค่า หากกลับมาเลือกมาตรฐานหรือว่าง ต้องไม่ส่งค่าช่องอื่น ๆ ที่ค้างอยู่

ตารางพนักงานยังมีช่องชื่อพนักงานรวมเพื่อไม่เพิ่มความกว้างตาราง ประกอบจากสามช่องเมื่อแสดง รองรับค้นหาชื่อ นามสกุล ชื่อเต็ม รหัส และข้อมูลที่ค้นหาได้เดิม ปรับข้อความช่วยอ่านของปุ่มแก้ไข/ลบและ dialog ยืนยันให้ใช้ชื่อที่ประกอบแล้ว จัดฟอร์มให้ใช้บนมือถือได้

## API และส่วนเชื่อมโยง

- รายการพนักงานคืนสามช่องแทนฟิลด์ `name` ของพนักงาน POST/PUT รับสามช่อง ตรวจและบันทึกแยกกัน
- แบบนี้เปลี่ยนสัญญาการเขียนชื่อพนักงาน: payload ที่ส่งเฉพาะ `name` ต้องได้ข้อผิดพลาดที่ชัดเจน ห้ามเดาแยกคำและห้ามรับแล้วทิ้งเงียบ ๆ ปรับเว็บ CLI fixtures และผู้เรียกใน repo ให้ใช้รูปแบบใหม่พร้อมกัน
- ส่วนอ้างอิงพนักงานในบัญชีผู้ใช้ และตัวเลือกผู้ปั๊ม ใช้สามช่องประกอบชื่อ ชื่อบัญชี `users.name` ยังคงเป็นข้อมูลแสดงของบัญชีตามเดิม
- ประวัติงานปั๊มและชุดชุบยังอ้าง employee id เดิม ปรับ SQL ที่อ่าน `employees.name` ให้ประกอบชื่อจากสามช่อง ฟิลด์ผลลัพธ์สำหรับแสดง เช่น `employee_name` หรือรายชื่อ workers เป็นค่าที่คำนวณ ไม่ใช่ข้อมูลชื่อที่เก็บซ้ำ
- พฤติกรรมประวัติเดิมยังเป็นการแสดงชื่อทะเบียนปัจจุบัน ไม่เพิ่ม snapshot ชื่อในงานย้อนหลัง
- ไม่เปลี่ยน users.name, roles.name, positions.name, ชื่อประเภทสินค้า หรือฟิลด์ name ของโดเมนอื่น
- สิทธิ์ employees.create/update/read/delete, การเชื่อมบัญชี และ audit actor/target ใช้กติกาเดิม บันทึกการเปลี่ยนข้อมูลจากการนำเข้าให้ตรวจย้อนกลับได้โดยไม่บันทึกเลขประจำตัวเต็มใน log

จุดที่ตรวจพบ: `apps/api/src/database.ts`, `app.ts`, `import.ts`, `commands.ts`, `pressing/catalog.ts`, `pressing/stock.ts`, `finishing/glazing.ts`; ฝั่งเว็บ `lib/types.ts`, `lib/model.ts`, `lib/pressing.ts`, `components/dialog.tsx`, `record-table.tsx`, `pressing/production.tsx` และผู้ใช้ชนิดข้อมูลเหล่านี้

ตรวจและปรับ `scripts/qa-server.mjs`, `enrich-employees.mjs`, `reconcile-data.mjs`, ตัวอย่าง payload และ tests ที่เขียนหรืออ่านชื่อรวมพนักงานด้วย ไม่ค้นแทนคำว่า name ทั้ง repo แบบเหมารวม

## ย้ายข้อมูลเดิมและนำเข้าทะเบียน

ผลตรวจอ่านอย่างเดียวก่อนออกแบบ: ฐาน Docker หลักมี 37 คน และไฟล์มี 36 คน ทั้ง 36 จับคู่คนเดิมได้ไม่ซ้ำ ไม่มีคนใหม่ที่ต้องเพิ่มในชุดข้อมูลนี้ การจับคู่ด้วยชื่อเป็นเพียงการเตรียม mapping ครั้งนี้ หลังตรวจแล้วผูก mapping ด้วย id/code และค่าเดิมที่คาดหมาย ไม่จับคู่ใหม่ด้วยชื่อที่ถูกแก้แล้ว

1. B เป็น prefix, C เป็น first_name, D เป็น last_name, G เป็น social_security_number, H เป็น taxpayer_id ใช้ C/D โดยตรง ชื่อหลายคำมีจริง ห้าม split ชื่อรวมแบบทั่วไป
2. คืนศูนย์นำหน้าที่หายเฉพาะ 8 ช่องที่พิสูจน์จากชนิดตัวเลขและรูปแบบแสดงผล 13 หลักของ Excel ไม่เติมศูนย์ให้เลขสั้นทุกค่าตามการเดา เก็บ Markdown ฉบับแก้ไขและ staging นอก Git พร้อม source hashes
3. สำหรับคนที่ 37 ใช้ mapping ส่วนตัวที่ตรวจไว้: คำนำหน้าว่าง และแยกชื่อ/นามสกุลตามสองส่วนที่ตรวจจากข้อมูลเดิม ไม่เติมคำนำหน้าหรือเลขประจำตัวเอง แสดง mapping นี้ให้ตรวจรับใน QA
4. เพิ่มสามช่อง เติมข้อมูลทั้ง 37 ตรวจทุกแถวและ constraints แล้วจึง drop คอลัมน์ name ภายในขั้นตอนเปลี่ยนโครงสร้างที่ควบคุมและทำ transaction ได้ ห้ามลบ name ก่อนมีข้อมูลแยกครบ ห้ามใส่ข้อความ placeholder เพื่อให้ผ่าน
5. migration เริ่มแอปต้องรองรับการรันซ้ำและฐานใหม่ ใช้การอัปเกรดที่ชัดเจนสำหรับฐานเก่า ห้ามแอปอ่านไฟล์ส่วนตัวแล้วเดาแยกชื่ออัตโนมัติทุกครั้งที่เริ่ม และห้ามรายงานสำเร็จหากยังต้องรอ mapping
6. ไม่แก้ id/code, โทรศัพท์, แผนก, ตำแหน่ง, สถานะ, วันที่สร้าง และความสัมพันธ์เดิม เก็บค่าเลขประจำตัวเดิมถ้าต้นทางว่าง ข้อยกเว้นการแทนค่าที่มีอยู่คือรายการทดสอบที่ผู้ใช้อนุมัติแล้ว
7. การนำเข้าต้องทำใน transaction พร้อม guard ค่าเดิมที่คาดไว้ ปฏิเสธความเปลี่ยนแปลงใหม่ที่ยังไม่ได้ตรวจแทนการเขียนทับ มี dry-run รายงานจำนวนการเปลี่ยนแปลง และรันซ้ำไม่เพิ่มคนซ้ำหรือเติมค่าซ้ำ

## ตัวนำเข้าเก่าและฐานใหม่

ตัวนำเข้า Excel ที่ใช้งานต่อปรับ payload ให้ส่งสามช่องและตรวจซ้ำจากชื่อที่ประกอบเพื่อรักษาพฤติกรรมตรวจ conflict เดิม แยกงานนำเข้าชุดนี้ออกจากตัวนำเข้าเก่าที่เพิ่มอย่างเดียว

SQLite เก่ายังคงอ่านคอลัมน์ตาม schema ต้นทางเดิม ไม่เพิ่มสามช่องเข้าไปใน SELECT จาก SQLite ที่ไม่มีคอลัมน์นั้น การย้ายพนักงานจาก legacy ต้องมี mapping แยกส่วนชื่อที่ตรวจแล้วตาม source employee id ก่อนเขียนฐานปลายทาง หากไม่มี mapping ให้หยุดทั้ง transaction พร้อมคำอธิบาย ไม่เดา split ชื่อสากล รักษา backup/guard ของตัว migrate เดิม และตรวจ fixtures ที่เกี่ยวข้อง

## การซ้อม การนำขึ้น และการย้อนกลับ

- หลังอนุมัติแบบจึงเขียนแผนและโค้ด สำรอง `lthai` ใน `lthai-docker` ใหม่ พร้อม SHA-256 ตาม docs/docker.md#docker-backup แล้ว restore เป็นฐาน QA คนละชื่อ
- ตรวจ current_database/server/เป้าหมายการเชื่อมต่อก่อน migration/test และให้เว็บ/API ทดสอบชี้ QA เท่านั้น เก็บข้อมูลส่วนตัวใน staging นอก Git
- ทดสอบ migration + import บน QA และเปิดเว็บให้ผู้ใช้ตรวจทั้งฟอร์มและข้อมูล ก่อนอนุมัติการนำขึ้นฐานหลัก
- หลังผู้ใช้ตรวจรับ สำรองฐานหลักใหม่อีกรอบ เทียบฐานปัจจุบันกับ mapping/ค่าเดิม หยุดหากข้อมูลที่เกี่ยวข้องเปลี่ยนและต้องตกลงใหม่ รักษารายการและการเปลี่ยนแปลงอื่นตั้งแต่ snapshot QA
- เนื่องจากลบคอลัมน์เดิม ต้องนำ API/web/schema ขึ้นพร้อมกันในช่วงหยุดรับการเขียนสั้น ๆ ไม่ปล่อย API เก่าเขียน schema ใหม่ ไม่ restore QA ทั้งฐานทับหลัก
- ตรวจฐานหลักและ UI จริง หลังผ่านเก็บ QA backup แล้วลบเฉพาะ QA containers/database ตาม AGENTS.md เก็บ backups ไว้
- หากอัปเกรดล้มเหลวก่อน commit ให้ rollback transaction หากต้องย้อนหลังนำขึ้น ให้หยุดการเขียน ประเมินข้อมูลใหม่ และใช้ขั้นตอนย้อน schema/code ที่ทดสอบใน QA โดยสร้างชื่อรวมจากสามช่องกลับมา ห้ามกู้ full backup ทับการเปลี่ยนแปลงใหม่โดยอัตโนมัติ

## หลักฐานที่ต้องผ่านก่อนอ้างว่าสำเร็จ

- ตรวจ schema ว่ามีสามช่องและไม่มี employees.name พร้อม migration รันซ้ำและฐานใหม่ที่สร้างได้จริง
- เทียบข้อมูล 37 คนกับ mapping ทุกช่อง ชุด36จากไฟล์ถูกต้อง ศูนย์นำหน้าครบ ไม่มี insert/delete พนักงานโดยไม่ตั้งใจ
- ทดสอบ first_name ว่างถูกปฏิเสธ prefix/last_name ว่างได้ ชื่อหลายคำ ต่างภาษา อื่น ๆ สลับตัวเลือก และค่าเก่าที่ไม่ได้ส่งไม่สูญหายตามสัญญา API ที่กำหนด
- ทดสอบ create/edit/read-back, ข้อผิดพลาด legacy name-only, ค้นชื่อเต็ม/นามสกุล, employee selectors, pressing history และ glazing names
- ตรวจ users.name/id และ foreign keys เดิม พร้อม fingerprints ตารางที่ไม่ควรเปลี่ยน ยืนยันสิทธิ์และ audit ใช้งานต่อ
- typecheck, ชุดทดสอบ API/web/import ที่ได้รับผลกระทบ, ชุดทดสอบรวมที่รันได้ และ production build รายงานข้อจำกัดตามจริง
- ตรวจเบราว์เซอร์บน QA ทั้งเพิ่ม/แก้ไข ตาราง งานปั๊ม งานชุบ บัญชีที่เชื่อมพนักงาน และมือถือก่อนขออนุมัติขึ้นหลัก

## สิ่งที่ผู้พัฒนาเลือกได้

ชื่อไฟล์ helper และโครงสร้าง validation, การใช้ SQL/TypeScript ประกอบชื่อในแต่ละขอบเขต, รูปแบบ staging แบบมี version, ชื่อฐาน/พอร์ต QA และการแบ่ง commit เลือกให้สอดคล้อง repo โดยไม่เปลี่ยนข้อตกลงข้างต้น คำนวณชื่อด้วยกติกาเดียวกันและมีการตรวจเทียบระหว่างส่วนแสดงผล
