# ทะเบียนประเภทดินและการเลือกในใบสั่งผลิต

วันที่: 23 พฤศจิกายน 2026
สถานะ: ผู้ใช้ยืนยัน Q4 เมื่อ 23 พฤศจิกายน 2026 ให้เริ่มวางแผนตามแบบนี้ ยังไม่อนุมัติลงมือพัฒนาหรือนำขึ้นหลัก

## เป้าหมายและข้อตกลง Q1–Q3

สร้างทะเบียนกลางชื่อ “ทะเบียนประเภทดิน” สำหรับดินขาว ดินสี ดินแดง และศิลาแลง ให้เลือกในใบสั่งผลิตและรักษาตัวตนดินตลอดงานปั๊ม เบิก ชุบ เผา QC และสต็อก สินค้ายังคงเป็นรายการเดิม ไม่สร้างสินค้าซ้ำสี่รายการตามดิน

- Q1 ผู้ใช้ต้องการทะเบียนสีที่ผสมในดินขาว แต่ยังไม่มีข้อมูลสี ให้เตรียมทะเบียนสีดินว่างไว้ เพิ่มภายหลังได้ ไม่สร้างสีตัวอย่างในข้อมูลที่จะนำขึ้นหลัก
- Q2 ผู้ใช้เลือกขอบเขตทะเบียนดิน ค่าผลิตที่จำเป็น การเลือกในใบสั่งและงานต่อเนื่อง ยังไม่ทำสูตรผสม เปอร์เซ็นต์สี การบันทึกผสมจริง และสต็อกวัตถุดิบ
- Q3 ผู้ใช้มีข้อมูลอุณหภูมิแต่ขอพักไว้ก่อน จะเรียบเรียงส่งภายหลัง ไม่เดาช่วงใหม่ และไม่เปิดหน้าตั้งค่ารายสีดินในงานนี้
- งานเพิ่มปุ่มลบทะเบียนกระเบื้องยกเลิกแล้ว ไม่เป็นส่วนหนึ่งของงานนี้

## ข้อเท็จจริงและแนวทางที่พิจารณา

ปัจจุบันประเภทดินเป็นข้อความสี่ค่าที่กำหนดใน API/เว็บและข้อจำกัดฐานข้อมูล ไม่มีทะเบียนกลาง สีดินอยู่ใน pressing_types.clay_color แบบข้อความ แยกจากชาร์ตสีที่อ้างด้วย color_id ใบสั่งเลือกประเภทผลิต type_id ซึ่งรวมแบบดินปั๊ม ดิน และสีดิน แล้วเก็บ snapshot ของค่าผลิต

แนวทางที่พิจารณา:

1. คงค่าดินไว้ในโค้ดและเพิ่มเฉพาะตัวเลือก: เปลี่ยนน้อย แต่ไม่ตอบโจทย์ทะเบียนในฐานข้อมูล
2. เพิ่มทะเบียนดินและสีดิน เชื่อมกับประเภทผลิตเดิม: เป็นแนวทางที่เสนอและสอดคล้องกับ Q1–Q2 รักษาการแยกสต็อกและประวัติโดยไม่สร้างระบบผลิตอีกชุด
3. สร้างระบบสูตรผสม/ล็อตดิน/วัตถุดิบ: เกินขอบเขตที่ผู้ใช้เลือกใน Q2 จึงพักไว้

อ้างอิงเอกลักษณ์สินค้า/แบบดินปั๊มตาม ADR0006 และเงื่อนไขค่าผลิต/ความพร้อมตามแบบทะเบียน 2026-11-20 ไม่รวมสินค้าหรือประเภทผลิตเดิมโดยเดาจากขนาด

## ชื่อและโครงสร้างฐานข้อมูลที่เสนอ

### clay_types — ประเภทดิน

- id: คีย์อ้างอิงถาวร
- code: รหัสระบบไม่ซ้ำและไม่เปลี่ยนหลังสร้าง ได้แก่ WHITE, COLORED, RED, LATERITE
- name: ชื่อแสดง ดินขาว ดินสี ดินแดง ศิลาแลง ตามลำดับ
- description: คำอธิบายเพิ่มเติมเมื่อมี
- base_clay_type_id: อ้างถึงดินขาวเฉพาะดินสี ประเภทอื่นไม่มีค่า
- active: ใช้/หยุดใช้สำหรับการเลือกในงานใหม่

เริ่มต้นสี่ประเภทตามคำสั่งผู้ใช้ ไม่เปิดเพิ่มประเภทที่ห้าในรุ่นนี้ รหัสกำหนดพฤติกรรม ส่วนชื่อแสดงแก้ได้โดยไม่เปลี่ยนตัวตนดิน ห้ามลบประเภทที่ถูกอ้างอิง ความสัมพันธ์ดินสี→ดินขาวเป็นคำอธิบายที่มาของดิน ไม่ทำให้ยอดสต็อกหรืองานของดินทั้งสองรวมกัน และไม่เกิดการหักวัตถุดิบอัตโนมัติ

### clay_colors — สีดิน

- id: คีย์อ้างอิงถาวร
- code: รหัสสีดินที่ผู้ดูแลกำหนด ไม่ซ้ำ
- name: ชื่อสีดินที่โรงงานยืนยัน
- notes: หมายเหตุเมื่อมี
- active: ใช้/หยุดใช้ในงานใหม่

เริ่มต้นว่าง ไม่ต้องกรอกสูตร อัตราส่วน หรือสีเคลือบ สีดินไม่ได้อ้างถึง color_chart_entries โดยอัตโนมัติ อนุญาตใช้เฉพาะประเภท COLORED

### ประเภทผลิตเดิม — pressing_types

เชื่อม clay_type_id และ clay_color_id กับทะเบียนใหม่ โดยรักษา id เดิมและ body_id ที่แทนแบบดินปั๊ม เอกลักษณ์ยังเป็นแบบดินปั๊ม + ประเภทดิน + สีดินเมื่อเป็นดินสี รายการดินสีพร้อมผลิตต้องมีสีดินที่ใช้งานได้ ประเภทอื่นไม่มี clay_color_id

จำนวนแผ่นต่อไม้ ระยะพัก จำนวนแผ่นต่อ ตร.ม. และเส้นทางชุบ/เข้าเตาคงอยู่ที่ค่าผลิตของแบบและดินนั้น ไม่ย้ายไปเป็นค่ากลางของดินสี่รายการ เพราะกระเบื้องต่างแบบอาจใช้ค่าต่างกัน

เตรียมทางตั้งค่าผลิตจากรายการสินค้า ใช้แบบดินปั๊มเดิมหรือสร้าง/ยืนยันแบบตามรายการจริง ไม่จับกลุ่มสินค้าร่วมแบบหรือคัดลอกค่าข้ามดินโดยอัตโนมัติ รักษากรณีใช้แบบร่วมที่ยืนยันไว้แล้ว หน้าทะเบียนสินค้าใช้ค้น/เพิ่ม/แก้ไขได้แม้ยังไม่มีค่าผลิต

ไม่สร้างค่าผลิตว่างโดยใส่ 0 หรือ 1 แทนข้อมูลที่ไม่ทราบ ผู้ใช้เลือกดูสินค้า/ประเภทดินได้ และเห็นข้อความ “รอตั้งค่าผลิต” สำหรับคู่ที่ยังไม่มีชุดค่าครบ จึงไม่จำเป็นต้องสร้าง pressing_types ที่ผิดข้อจำกัดเดิมเพื่อแทนช่องว่าง

### ใบสั่งผลิตและข้อมูลต่อเนื่อง

ใบสั่งอ้าง type_id เดิม พร้อมอ้างประเภทดิน/สีดินด้วย ID และเก็บชื่อดิน ชื่อสีดิน และค่าผลิตขณะสร้างใบสั่ง การเปลี่ยนชื่อหรือค่าเริ่มต้นภายหลังไม่เขียนทับประวัติใบเดิม

การแสดงผลและกติกาธุรกิจใช้ตัวตนอ้างอิง ไม่ใช้ชื่อแสดงเป็นคีย์จับคู่ ข้อมูล snapshot ยังคงไว้เพื่ออธิบายประวัติ การหยุดใช้ทะเบียนป้องกันการเลือกในใบใหม่ แต่ไม่หยุดงานเดิมที่เปิดถูกต้องแล้ว

## การเลือกและความพร้อมใช้งาน

ลำดับ: สินค้า → ประเภทดิน → สีดินเฉพาะดินสี → ตรวจ/แสดงค่าผลิต → บันทึกใบสั่ง

- สี่ประเภทดินมีในทะเบียนได้ทันที แม้ยังไม่มีค่าผลิต
- ดินสีที่ยังไม่มีข้อมูลสี: แสดงเหตุผลว่ายังไม่มีสีดินให้เลือก ไม่เปิดใบสั่งดินสีด้วยค่าว่างหรือสีสมมติ
- ดินขาว/ดินแดง/ศิลาแลง: เปิดใบสั่งได้เมื่อมีแบบและค่าผลิตครบจริง ไม่ต้องรอทะเบียนสีดิน
- ค่าผลิตต้องยืนยันจำนวนแผ่นต่อไม้ >0, วันพัก >=0, จำนวนแผ่นต่อ ตร.ม. >0 และเส้นทางผลิต ไม่เดาตัวเลขจากชื่อหรือขนาดสินค้า
- สีเคลือบยังเลือกแยกจากสีดินตามเส้นทางผลิตและกติกาเดิม
- การไม่มีช่วงอุณหภูมิใหม่ไม่บล็อกการเก็บทะเบียนหรือเปิดใบสั่งที่ค่าผลิตครบ ส่วนการจัดเข้าเตาต้องผ่านการตรวจช่วงอุณหภูมิตามระบบเดิม ไม่ข้ามการตรวจเพราะงานนี้พักข้อมูลอุณหภูมิ
- คงค่าช่วงอุณหภูมิที่มีอยู่ ไม่สร้างค่าทดแทนหรือช่วงรายสีดินที่ยังไม่ได้รับ ข้อมูลที่ผู้ใช้จะส่งภายหลังเป็นงานต่อเนื่อง

## งานต่อเนื่องและความเข้ากันได้

- ปั๊มและสต็อกดินปั๊ม: ใช้ประเภทผลิตเดิมเป็นหลักในการแยกแบบ/ดิน/สีดิน การเพิ่มทะเบียนไม่ย้ายยอดระหว่างประเภท
- เบิกและชุบ: ตรวจประเภทผลิตและตัวตนดินให้ตรงใบสั่ง ห้ามแทนดินขาวด้วยดินสีหรือรวมดินสีต่างสี
- เผาและ workflow: เชื่อมตัวตนใหม่กับกติกาอุณหภูมิเดิม รักษา JSON state/event และ snapshot ย้อนหลัง ไม่แทนชื่อย้อนหลังแบบเหมารวม
- QC และสินค้าสำเร็จ: คงการแยกสินค้า ประเภทผลิต สีดิน สีเคลือบ และเกรดตามกติกาปัจจุบัน
- บัญชีที่อ่านได้อย่างเดียวไม่มีสิทธิ์เปลี่ยนทะเบียน ใช้สิทธิ์จัดการงานผลิตเดิม บันทึก audit เมื่อสร้าง/แก้ไข/หยุดใช้ทะเบียนและค่าผลิต

## การย้ายข้อมูล

เพิ่ม ID ควบคู่กับข้อความเดิมในช่วงย้ายข้อมูล จับคู่ข้อความแดง/ขาว/สี/ศิลาแลงกับสี่ประเภทโดยตรง ตรวจค่าที่ไม่รู้จักและหยุดแทนการเดา ไม่เปลี่ยน id ของสินค้า/ประเภทผลิต ไม่รวมประวัติเดิม

หากสำเนาล่าสุดมีข้อความสีดินเดิม ให้จัดทำรายงานเพื่อยืนยันการจับคู่กับทะเบียนสีดิน ไม่สร้างรหัสสีหรือรวมชื่อคล้ายกันโดยอัตโนมัติ รายการเดิมยังอ่าน/ทำงานต่อด้วยข้อมูลเดิมได้ระหว่างรอยืนยัน แต่ไม่ถือว่าพร้อมให้เลือกในใบสั่งใหม่จนจับคู่ครบ

เก็บข้อความ snapshot เดิมไว้เป็นหลักฐาน ตรวจทุกจุดที่ใช้ข้อความดินเปรียบเทียบ/จัดกลุ่ม รวม CHECK/index, stock, finishing และ workflow ให้รองรับ ID โดยยังแปลข้อความเดิมสำหรับประวัติและการทำงานระหว่างย้ายข้อมูล ห้ามเปลี่ยนชื่อแสดงให้ทำลายการจับคู่ช่วงอุณหภูมิเดิม

## วิธีตรวจรับและนำขึ้นหลัก

ก่อนทดสอบ สำรอง Docker lthai ใหม่ ตรวจ checksum/archive แล้วกู้เป็นฐาน QA แยกพร้อมผู้ใช้เฉพาะ ตรวจ database/role ก่อน migration/tests ทดสอบเขียนเฉพาะ QA

ตรวจทะเบียนสี่ประเภทและทะเบียนสีดินว่าง; เติมสีเฉพาะ QA เพื่อทดสอบ; เปิดใบสั่งจากค่าผลิตจริงที่ยืนยัน; บล็อกสีดิน/ค่าผลิตที่ขาด; ตรวจการแยกสต็อกและข้อมูลต่อเนื่อง; เปลี่ยนชื่อ/หยุดใช้แล้วประวัติเดิมไม่เปลี่ยน; ตรวจงานเตายังคงตรวจอุณหภูมิและสิทธิ์อ่าน/จัดการตามเดิม

ผู้ใช้ต้องยืนยันโมดูลและข้อมูลที่จะเก็บก่อนนำขึ้นหลัก สำรองหลักใหม่อีกครั้ง ย้ายเฉพาะ code/migrations/ข้อมูลที่อนุมัติ รักษาการเปลี่ยนแปลงหลังสำเนา QA ห้าม restore QA ทับหลัก ทดสอบหลักแล้วจึงลบ stack/ฐาน QA โดยเก็บ backups

## สิ่งที่ผู้พัฒนาตัดสินใจได้ภายใต้แบบนี้

รายละเอียด migration แบบเพิ่มคอลัมน์ ลำดับปรับ queries และรูปแบบฟอร์มให้เข้ากับระบบเดิมตัดสินใจได้ระหว่างวางแผน แต่ห้ามเดาข้อมูลโรงงาน เพิ่มการหักวัตถุดิบ ทำสูตรผสม เปิดประเภทดินใหม่ หรือยกเลิกกติกาความพร้อม/อุณหภูมิโดยไม่กลับมาหารือ
