# ชาร์ตสีพร้อมอุณหภูมิอ้างอิง

วันที่: 23 พฤศจิกายน 2026
สถานะ: ผู้ใช้ยืนยันแบบ23พฤศจิกายน2026 พร้อมให้จัดทำแผน ยังไม่อนุมัติการลงมือหรือการนำขึ้นหลัก

## เป้าหมายและข้อตกลง

แสดงชื่อ รูป หมายเหตุ และอุณหภูมิอ้างอิงของสีในหน้าชาร์ตสีเดียวกัน เริ่มหนึ่งค่าอุณหภูมิต่อหนึ่งสี ไม่แยกตามประเภทดินในรุ่นนี้ ผู้ใช้ยืนยันชื่อช่อง “อุณหภูมิอ้างอิง (°C)” และเว้นว่างได้ สีที่ยังไม่มีข้อมูลแสดง “ยังไม่ระบุ”

สีในขอบเขตนี้คือสีในชาร์ตสี ไม่ใช่สีดินที่ผสมในเนื้อดิน เบอร์โคนเป็นข้อมูลที่จดประจำการเผาแต่ละครั้ง ไม่ผูกกับทะเบียนสีหรือประเภทดิน และไม่ใช้คำนวณอุณหภูมิของสีอัตโนมัติ

ค่าใหม่นี้ใช้แสดงข้อมูลเท่านั้น เก็บช่วงต่ำสุด–สูงสุดและกติกาเข้าเตาเดิมไว้ รอข้อมูลครบแล้วจึงออกแบบเปลี่ยนกติกาแยกต่างหาก ไม่ใช้ค่าอ้างอิงแทนช่วงเดิม ไม่ตั้ง minimum=maximum และไม่เติมค่าเริ่มต้นที่เดาขึ้นมา

## ทางเลือกและข้อเสนอ

1. เพิ่มคอลัมน์อุณหภูมิในทะเบียนสี: เรียบง่าย แต่ทำให้ข้อมูลทะเบียนกับค่าการเผาอยู่ในรายการเดียวกันและต้องแยกการเขียนตามสิทธิ์อย่างระวัง
2. เพิ่มค่าเดียวในตารางช่วงอุณหภูมิเดิม: ใช้ข้อมูลการเผาร่วมกันได้ แต่ตารางปัจจุบันบังคับ minimum/maximum และถูกใช้ตรวจเข้าเตา มีสีอ้างอิงจากประวัติที่ไม่ได้อยู่ในทะเบียนปัจจุบันด้วย การปรับตารางนี้เพิ่มความเสี่ยงแก่กติกาที่ไม่อยู่ในขอบเขต
3. แยกตารางอุณหภูมิอ้างอิงของสี: เพิ่มเพียงหนึ่งตาราง เชื่อมกับรหัสสีจริง ไม่เปลี่ยนตารางช่วงและการตรวจเข้าเตาเดิม

ผู้ใช้ยืนยันทางเลือก3พร้อมแบบ เพื่อแยกการแสดงข้อมูลใหม่ออกจากกติกาปฏิบัติงานเดิม

## โครงสร้างข้อมูลที่เสนอ

ฐาน PostgreSQL เดิม ไม่สร้างฐานแยก:

| ข้อมูล | ที่เก็บ |
|---|---|
| ตัวตน ชื่อ ลำดับ หมายเหตุสี | `color_chart_entries` เดิม |
| รูปตัวอย่าง | `color_chart_images` เดิม |
| อุณหภูมิอ้างอิง | ตารางใหม่ `color_reference_temperatures` |
| ช่วงเผาของสี | `firing_color_ranges` เดิม |
| ช่วงดิน/ประเภทผลิต และบันทึกเผา/โคน | ที่เก็บเดิม ไม่ย้ายในงานนี้ |

ตารางใหม่มี `color_id` เป็น primary key และ foreign key ไป `color_chart_entries.id` กับ `temperature_c` เป็นตัวเลขค่าจำกัดที่มากกว่า0 รองรับทศนิยมได้ ไม่จำกัดให้เป็นจำนวนเต็มโดยไม่มีข้อมูลหน้างาน หนึ่งสีมีอุณหภูมิอ้างอิงได้ไม่เกินหนึ่งรายการ ไม่มีแถวหมายถึงยังไม่ระบุ การล้างค่าคือเอารายการอ้างอิงของสีนั้นออกและบันทึกประวัติ

ข้อเสนอเชิงรายละเอียด: ใช้ ON DELETE CASCADE เฉพาะค่าอ้างอิงใหม่นี้เมื่อการลบสีผ่านกติกาเดิมสำเร็จ ไม่เปลี่ยนกติกาลบสีเดิม ไม่ลบหรือย้ายช่วงเผา ใบสั่ง หรือประวัติการผลิตตามไปด้วย

เริ่มตารางใหม่ว่าง ไม่ย้ายหรือเดาค่าจากช่วงต่ำสุด–สูงสุด ไม่จับคู่จากชื่อ ไม่แปลงเบอร์โคนเป็นค่าอ้างอิง และยังไม่นำเข้าชุดข้อมูลจริงที่ผู้ใช้ยังไม่ได้สรุป

## การแสดงผลและสิทธิ์

- รายการชาร์ตสีแสดงชื่อ รูป และอุณหภูมิอ้างอิงหรือ “ยังไม่ระบุ”; หน้ารายละเอียดแสดงหมายเหตุเดิมด้วย
- ผู้มี `color_chart.read` ดูค่าอ้างอิงได้ในหน้าชาร์ตสี ไม่เพิ่มเงื่อนไขว่าต้องมีสิทธิ์ดูงานเผาด้วย
- ในรายละเอียดสีมีส่วนแก้ “อุณหภูมิอ้างอิง (°C)” สำหรับผู้มีทั้งสิทธิ์อ่านชาร์ตสีและ `finishing.temperature` โดยไม่ต้องมี `color_chart.manage`
- ชื่อ หมายเหตุ รูป และการจัดการสีใช้สิทธิ์เดิม ผู้มีเฉพาะสิทธิ์แก้สีเปลี่ยนอุณหภูมิไม่ได้
- แยกการบันทึกอุณหภูมิจากการบันทึกชื่อ/หมายเหตุ/รูป ไม่ส่งหรือเขียนฟิลด์ที่ผู้ใช้ไม่มีสิทธิ์ API ต้องตรวจสิทธิ์ซ้ำและบันทึกผู้แก้พร้อมค่าก่อน/หลัง
- ช่วงต่ำสุด–สูงสุดและหน้าตั้งค่าช่วงเดิมยังคงอยู่ การเพิ่มฟิลด์ใหม่ไม่ปิดความสามารถเดิมหรือเปลี่ยนการตรวจเข้าเตา

## ขอบเขตที่ไม่รวม

ไม่แก้สีดิน ไม่ทำทะเบียนโคนหรือสูตรแปลงโคน ไม่เพิ่มหลายอุณหภูมิต่อสี ไม่แยกตามดิน ไม่สร้างโปรแกรมเผา ไม่เปลี่ยนการจัดงานร่วมเตาและไม่เขียนประวัติรอบเผาเก่าใหม่

## เกณฑ์ตรวจรับและการนำขึ้น

ตรวจสีที่มีค่า/ไม่มีค่า แก้และล้างค่า ทศนิยม/ค่าผิด การเปลี่ยนชื่อสีที่ไม่กระทบตัวตน และสิทธิ์อ่าน/แก้สี/ตั้งอุณหภูมิแยกกัน ตรวจว่าการบันทึกชื่อหรือรูปไม่เปลี่ยนค่าอ้างอิง ตรวจกรณีสีถูกลบระหว่างเปิดรายละเอียดโดยไม่สร้างข้อมูลกำพร้า

ยืนยันช่วงเดิม กติกาเข้าเตา และประวัติเผายังทำงานเหมือนเดิม ตรวจหน้าเว็บคอมและมือถือ การทดสอบเขียนข้อมูลต้องใช้ QA ตาม AGENTS.md: สำรองหลักใหม่ กู้แยกและตรวจ target ก่อน migration/tests ให้ผู้ใช้ตรวจรับโมดูลและเลือกข้อมูลที่จะเก็บก่อนนำขึ้นหลัก หลังตรวจหลักผ่านจึงสำรองและลบ QA
