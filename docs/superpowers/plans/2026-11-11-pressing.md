# Pressing v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** ให้ธุรการบันทึกยอดปั๊มครั้งเดียวและใช้ยอดนั้นติดตามใบสั่งผลิต สต็อก การเบิก และผลคัดหลังเผา

**Architecture:** เพิ่มงานปั๊มภายใต้ API และ workspace เดิม ใช้ PostgreSQL เก็บยอดรับจากรายการปั๊มหรือยอดตั้งต้นพร้อมประวัติการเบิก ปล่อยยอดเกิน และปรับยอด การนับผลคัดอยู่ที่งานเผาและอ้างถึงงานปั๊มเมื่อมีข้อมูลตามกลับได้

**Tech Stack:** Node ≥26, TypeScript, Next.js/React/Tailwind, Express, PostgreSQL 18, Docker Compose, `node:test` และ `tsx` ที่มีอยู่

**Spec:** [แบบระบบงานปั๊มรุ่นแรก](../specs/2026-11-11-pressing-design.md) ผู้ใช้ยืนยันวันที่ 2026-11-11

## Global Constraints

- ใช้ระบบบัญชีและสิทธิ์เดิมผ่านเว็บในเครือข่ายโรงงาน เว็บ Docker พอร์ต 3001 และ PostgreSQL พอร์ต 5434 พอร์ต 5433 เป็นฐานเดิมแยกกัน
- หน่วยสต็อกคือแผ่น จำนวนแผ่น = ไม้เต็ม × แผ่นต่อไม้ + แผ่นเศษ ประเภทดินคือแดง ขาว จ้อ และสี คำนวณ ตร.ม. เมื่อมีอัตราที่ตรวจแล้ว
- ใช้วันปฏิทินโรงงาน `Asia/Bangkok` สำหรับวันที่ปั๊มและครบพัก เก็บวันที่ทางธุรกิจเป็น PostgreSQL `date` และ API เป็น `YYYY-MM-DD` เก็บเวลาที่ผู้ใช้บันทึกเป็น `timestamptz`
- รับสต็อกเมื่อบันทึกยอดปั๊ม ลดเมื่อยืนยันเบิก ผู้เบิกตรวจสภาพจริงในวันครบพักหรือหลังจากนั้น บรีสเข้าเตาโดยข้ามงานสี
- ผลคัดตัดยอดเสียที่งานเผา การปล่อยส่วนเกินเปลี่ยนสิทธิ์ใช้ยอดเดิม การเบิกซ้ำและการส่งผลคัดซ้ำต้องรักษายอดเดิม
- ข้อมูลตั้งต้นคือประเภทกระเบื้อง แผ่นต่อไม้ และยอดคงเหลือที่หน้างานยืนยัน ใช้ข้อมูลสังเคราะห์ในการพัฒนาและทดสอบ เก็บไฟล์ Excel ข้อมูลตรวจนำเข้า `.env` และสำรองฐานภายนอก Git
- ใช้ตารางปกติใน schema `public` ในฐานใช้งาน เพื่อให้ชุดส่งต่อเดิมสำรองและตรวจข้อมูลได้ ใช้ฐานทดสอบแยกสำหรับทดสอบ migration, API และกู้คืน
- รุ่นแรกอ้างเลขออเดอร์จากงานขาย ส่วนค่าแรง ต้นทุนดิน งานสีและงานเตาเต็มรูปแบบ และประวัติผลิตย้อนหลังเป็นงานถัดไป

## Review Focus

1. ผู้ดูแลที่สร้างจากฐานเดิมต้องเข้าถึงสิทธิ์ใหม่หลัง migration บทบาทอื่นคงสิทธิ์เดิม (Task 1)
2. การแก้จำนวนแผ่นต่อไม้หรือวันพักต้องคงผลคำนวณของรายการปั๊มเดิม (Task 2)
3. ผู้เบิกสองคนแย่งยอดเดียวกัน และกดซ้ำหลังการเชื่อมต่อหลุด ต้องไม่ตัดยอดเกินหรือซ้ำ (Task 3)
4. ส่วนเกินที่ปล่อยแล้วถูกเบิกไปใช้กับงานอื่น การปรับยอดต้นทางต้องคุ้มครองจำนวนที่ปล่อยโดยไม่หักส่วนเดียวกันสองครั้ง (Task 4)
5. คัดรวมหลายคน แก้ผลหลังส่งแล้ว และส่งคำขอเดิมซ้ำ ต้องนับผลคัดครั้งเดียวและคงสต็อกงานปั๊ม (Task 5)

### Task 1 — ทะเบียนประเภท ใบสั่งผลิต และสิทธิ์

### Task 4 — ปรับยอดโดยรักษารายการเดิม

**Interfaces:** `PUT /entries/:id` ใช้ฟิลด์วันที่ ผู้ปั๊ม จำนวนไม้ เศษ และหมายเหตุเดิมสำหรับรายการที่ยังไม่ถูกเบิกหรือปล่อย `POST /entries/:id/adjustments` รับ `{ request_id, corrected_pieces, reason }` `POST /issues/:id/reversals` รับ `{ request_id, lines: { issue_line_id, pieces }[], reason }` สำหรับการแก้รายการเบิกที่ลงผิด ผู้ปรับต้องมี `pressing.correct` ใช้ `GET /entries/:id/adjustments` และ `GET /issues/:id/reversals` เปิดดูค่าก่อนแก้ จำนวน เหตุผล ผู้แก้ และเวลาย้อนหลัง

- [ ] รันชุด API ใน Task 1 และ `npm run check` คาดว่าผ่าน ตรวจว่าการเปลี่ยนเป้าใบสั่งเพียงอย่างเดียวไม่ปล่อยยอดเอง
